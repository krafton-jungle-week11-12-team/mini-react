# 테스트 케이스 작성

입력: `$ARGUMENTS`

이 스킬이 고치는 파일은 `src/**/*.test.ts`예요. 요구사항, 설계, ADR 문서와 테스트가 아닌 `src/` 코드는 읽고 보고만 해요. 테스트 문서는 만들지 않아요.

## 0. 입력 확인

- 첫 단어는 Phase예요. `.claude/skills/README.md`의 "Phase 인자" 절대로 읽어요.
- 둘째 단어부터는 대상이에요. 요구사항 문서 경로(예: `docs/requirements/phase2/use-memo_requirement.md`)나 요구사항 ID(예: `FR-M01 FR-M02`)를 받아요. 없으면 그 Phase의 요구사항 문서 전체를 대상으로 해요.
- 준 경로나 ID가 요구사항 문서에 없으면 멈추고 알려요.

## 1. 요구사항 완성 확인

`.claude/skills/design-doc/SKILL.md` 1단계 "요구사항 문서 완성 확인"을 따라요. 결과 표, 멈추는 조건, AskUserQuestion 선택지도 그대로 따라요. 단, "완성된 문서만 설계"는 "완성된 문서만 테스트 작성"으로 읽어요.

## 2. 읽을 문서

작성 전에 아래를 모두 읽어요.

1. 대상 요구사항 문서 — 3절 용어, 4절 동작 흐름, 5절 기능 요구사항과 확인 방법(초안), 6절 결정된 항목
2. 이 Phase의 설계 문서 (위치는 README "Phase 인자" 절) — 인터페이스, 자료구조, 경계 케이스, 검증 방법. 테스트 케이스는 요구사항이 기준이고 설계와 따로 만들 수 있어서, 설계 문서가 아직 없으면 건너뛰고 요구사항 3절 용어와 4절 흐름으로 함수 이름을 정해요. 그렇게 정한 이름은 마지막 보고에 적어요.
3. `docs/adr/` — 요구사항 비고에 `ADR-<번호> 승인 시 수정`이 붙은 ADR
4. `src/` — 테스트할 모듈의 실제 export와 시그니처, 같은 모듈의 기존 `*.test.ts`
5. `vitest.config.ts`, `package.json`의 `test` 스크립트

## 3. 계획 확인

- 테스트 파일은 테스트할 모듈 옆에 `<모듈>.test.ts`로 둬요. 이미 있으면 그 파일에 더해요.
- 쓰기 전에 아래 표를 보여 주고 확인을 받아요.

| 테스트 파일 | 테스트할 모듈 | 다루는 요구사항 ID | 새로 작성 / 더하기 |
| ----------- | ------------- | ------------------ | ------------------ |

- 테스트할 모듈이 아직 없으면 설계 문서 "인터페이스"의 이름과 시그니처로 import해요. 구현 전이라 실패한다고 표에 적어요.

## 4. 작성

### 형식 지키기

같은 모듈의 기존 테스트 파일 관례를 따라요. 기존 파일이 없으면 `src/diff.test.ts`를 기준으로 해요.

- 파일 맨 위 주석에 관련 설계 문서 경로를 적어요.
- `describe`·`it` 이름과 주석은 한국어로 쓰고, 케이스마다 요구사항 ID(`FR-…`)를 적어요.
- DOM이 필요하면 jsdom의 `document`를 쓰고, HTML 입력은 브라우저가 파싱한 결과로 만들어요.

### 기본 테스트 케이스

요구사항에서 바로 나오는 케이스예요. 사용자에게 묻지 않고 써요.

- 비고가 "삭제됨"이 아닌 요구사항마다 케이스를 하나 이상 둬요.
- 확인 방법(초안)을 실제 입력 값과 `expect`로 바꿔요.
- 요구사항 유형을 따라요. 이벤트(When)는 그 이벤트를 일으키는 호출을, 오류(If)는 오류 조건과 기대하는 처리를, 상태(While)는 그 상태를 만드는 준비를 써요.
- 요구사항과 설계에 없는 동작을 기대 결과로 만들지 않아요.
- 단위 테스트로 확인할 수 없는 요구사항(검증 페이지에서 눈으로 보는 것 등)은 테스트를 쓰지 않고 마지막 보고에 이유와 함께 적어요.
- `ADR-<번호> 승인 시 수정`이 붙은 요구사항의 케이스에는 바뀔 수 있다는 주석을 달아요.

### 추가 테스트 케이스 제안

기본 케이스를 다 쓴 뒤, 요구사항에는 없지만 있으면 좋을 케이스를 모아요.

- 설계 문서 "경계 케이스" 중 기본 케이스가 다루지 않는 것
- 빈 값, 경계 값, 같은 동작 반복, 순서가 바뀐 입력, 오류 뒤 상태처럼 요구사항이 말하지 않는 경우
- 두 모듈이 이어지는 곳 (요구사항 4절 흐름에서 앞 단계 결과를 다음 단계가 받는 곳)

모은 케이스를 아래 표로 보여 줘요.

| # | 제안 케이스 | 입력 | 기대 결과 | 근거 (설계 문서 경계 케이스 / 흐름 / 기타) | 관련 요구사항 |
| - | ----------- | ---- | --------- | ------------------------------------------ | ------------- |

그다음 반드시 AskUserQuestion으로 "이 테스트케이스도 추가할까요?"라고 물어요. 제안이 없으면 "추가로 제안할 테스트 케이스가 없어요"라고 알리고 넘어가요.

- **모두 추가** (추천): 표의 케이스를 전부 테스트로 써요.
- **일부만 추가**: 번호를 받아 그 케이스만 써요.
- **추가하지 않음**: 쓰지 않아요.

추가한 케이스의 기대 결과가 요구사항에 없는 새 동작이면, 마지막 보고의 "요구사항에 더할 것"에 적어요. 요구사항 문서는 고치지 않아요.

## 5. 검증

1. **커버리지**: 대상 요구사항 ID가 모두 테스트 주석에 있거나, "테스트하지 않는 요구사항"에 이유와 함께 있어요.
2. **없는 ID 참조**: 테스트에 적은 요구사항 ID가 실제 요구사항 문서에 있어요.
3. **타입 검사**: `npm run typecheck`가 통과해요. 구현 전이라 import할 모듈이 없어서 실패하는 것은 보고에 적어요.
4. **실행**: `npm test`로 테스트를 돌려요. 구현 전이라 실패하는 케이스는 실패로 두고, 테스트 코드 자체의 오류(문법, 잘못된 import 경로)만 고쳐요.
5. **문서 검수**: 이 스킬은 문서를 쓰지 않아요. 보고에 "검수할 문서 없음"이라고 적어요.

검증 결과는 아래 형식으로 보고해요.

| # | 항목 | 결과 | 문제 위치 | 고칠 내용 |
| - | ---- | ---- | --------- | --------- |

- 이번에 쓴 테스트의 문제는 바로 고치고 다시 검증해요.
- 구현 코드, 요구사항, 설계 문서를 고쳐야 하는 문제는 고치지 않고 보고만 해요.

## 6. 마지막 보고

- 작성·수정한 테스트 파일과 더한 케이스 수
- 검증 결과 표 (`npm test` 통과·실패 수 포함)
- 추가한 제안 케이스와 추가하지 않은 제안
- 테스트하지 않는 요구사항과 이유
- 요구사항에 더할 것: 추가 케이스에서 나온 새 동작, 확인 방법대로 해도 기대 결과가 나오지 않는 곳. 없으면 "없음"
