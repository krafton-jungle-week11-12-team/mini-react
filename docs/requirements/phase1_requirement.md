## 1. 목표

- Virtual DOM, Diff, Patch를 직접 구현해 **바뀐 노드만 실제 페이지 DOM에 반영**하는 흐름을 만든다.
- 테스트 웹 페이지에서 사용자가 HTML 코드를 입력하는 공간에서 HTML 코드를 고치고 Patch하면, 실제 영역의 바뀐 노드만 고쳐지고 두 영역의 렌더링 결과가 같아지는 것을 확인할 수 있어야 한다.
- 뒤로가기, 앞으로가기로 기록을 이동할 수 있어야 한다.

## 2. 범위

### 2.1 포함

- Virtual DOM 생성 (DOM 트리 → Virtual DOM 트리 변환, Virtual DOM 트리 → DOM 변환)
  - Virtual DOM 트리 → DOM 변환은 화면 렌더링용이 아니라, Patch가 새 노드를 만들 때 사용한다.
- Diff (두 Virtual DOM 트리 비교)
- Patch (바뀐 노드만 실제 DOM에 반영)
- 테스트 웹 페이지 기본 동작
  - 실제 영역과 테스트 영역
  - HTML 코드 표시와 수정
  - Patch 버튼, 바뀐 노드 강조 표시
  - State History, 뒤로가기, 앞으로가기
- 2차 추가 기능 (기본 기능 완료 후 구현, 5.3절)
  - State History 목록
  - Virtual DOM 시각화, Diff 결과 표시
  - Diff 종류별 샘플 HTML 코드 선택

### 2.2 제외

| 제외 항목                              | 이유                                                                                                                      |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Phase 2 항목 (Component, State, Hooks) | Phase 2에서 구현한다. AI에게 줄 문서라서 적어 두지 않으면 구현에 섞여 들어갈 수 있다.                                     |
| 외부 프레임워크 (React, Vue 등)        | Virtual DOM, Diff, Patch를 직접 구현하는 것이 과제 목적이다.                                                              |
| HTML 에디터 구현                       | HTML 코드 입력은 기본 입력창(textarea) 수준으로 한다. 문법 강조, 자동 완성 같은 에디터 기능은 만들지 않는다.              |
| 외부 시각화 도구                       | Virtual DOM 시각화, Diff 결과 표시는 외부 라이브러리 없이 화면에 직접 표시한다.                                           |
| 웹 디자인                              | 화면 배치는 동작 확인에 필요한 수준으로만 한다.                                                                           |
| 스크립트 실행 차단                     | 학습용 페이지라 사용자가 입력한 `<script>`, 이벤트 속성(`onerror` 등)의 실행을 막는 기능은 다루지 않는다. (협의 필요) |
| HTML 유효성 검사                       | 두 영역 모두 브라우저가 HTML 코드를 파싱하면서 보정하므로 직접 검사하지 않는다.                                           |

> 범위 포함 / 제외 근거는 통합 문서 AI 검수 때 다시 확인한다.

## 3. 용어

| 용어             | 뜻                                                                                                                      |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 실제 영역        | 샘플 HTML 코드로 처음 만들어지고, Patch로 바뀐 노드만 고쳐지는 영역                                                     |
| 테스트 영역      | 사용자가 HTML 코드를 수정하는 영역                                                                                      |
| 영역 컨테이너    | 실제 영역, 테스트 영역의 렌더링 결과를 담는 요소. Virtual DOM 변환은 `document`가 아니라 이 요소의 자식부터 시작한다. |
| DOM 트리         | 브라우저가 HTML 코드를 파싱해 만든 노드 트리. 문서 전체의 루트 노드는 `document`다.                                   |
| Virtual DOM 트리 | DOM 트리와 같은 구조를, 태그, 속성, 자식만 담은 JavaScript 객체로 나타낸 트리                                           |
| 바뀐 노드        | Diff로 찾은, 이전 Virtual DOM 트리와 새 Virtual DOM 트리 사이에서 달라진 노드                                           |
| 교체             | 같은 위치의 노드가 태그가 다르거나 노드 종류(요소 노드, 텍스트 노드)가 달라 통째로 바꾸는 경우                          |
| State History    | 기록의 상태를 순서대로 쌓아 두는 저장소                                                                                 |
| 기록의 상태      | 한 시점의 HTML 코드 원문(`html`)과 Virtual DOM 트리(`vdom`) 한 쌍. `{ html, vdom }`                               |

## 4. 동작 흐름

> 원칙: 렌더링 결과는 항상 HTML 코드를 브라우저가 파싱한 DOM으로 만든다. Virtual DOM 트리는 렌더링 결과를 만드는 데 쓰지 않는다.
> 실제 영역의 DOM과 테스트 영역의 DOM은 서로 다른 DOM이다.

### 4.1 페이지 로드

1. 실제 영역에 샘플 HTML 코드가 주어진다.
2. 브라우저가 샘플 HTML 코드를 파싱해 DOM을 만들고, 그 DOM으로 실제 영역의 렌더링 결과를 만든다.
3. 테스트 영역의 HTML 코드는 샘플 HTML 코드와 같고, 브라우저가 그 HTML 코드를 파싱한 DOM으로 테스트 영역의 렌더링 결과를 만든다.
4. DOM API로 실제 영역의 DOM 트리를 읽어 Virtual DOM 트리로 변환한다. (첫 기록 저장용)
5. `{ html: 샘플 HTML 코드, vdom: 4단계 변환 결과 }`를 `history[0]`으로 State History에 저장한다.

### 4.2 Patch

1. 사용자가 테스트 영역의 HTML 코드를 고치고 Patch 버튼을 누른다.
2. 수정한 HTML 코드로 DOM을 만들고, 그 DOM으로 테스트 영역의 렌더링 결과를 만든다.
3. 그 DOM 트리를 새 Virtual DOM 트리로 변환한다.
4. 현재 위치 기록의 `vdom`과 새 Virtual DOM 트리를 Diff로 비교해 바뀐 노드를 찾는다.
5. 바뀐 노드에 대해서만 DOM API를 호출해 실제 영역의 DOM을 고치고, 바뀐 노드를 강조 표시한다.
6. 두 영역의 렌더링 결과가 같은지 확인하고, 새 `{ html, vdom }`을 State History에 저장한다.

### 4.3 뒤로가기, 앞으로가기

- 두 영역의 렌더링 결과와 HTML 코드를 이동한 기록의 상태로 바꾼다.
- 이동할 때 테스트 영역은 기록의 `html`을 파싱한 DOM으로 렌더링 결과를 만든다.
- Patch와 달리 바뀐 노드만 고치는 것이 아니라 기록의 상태 전체로 바꾼다. (실제 영역 복원 방식은 설계에서 확정)

## 5. 기능 요구사항

> 확인 방법은 초안이다. 테스트 문서를 작성할 때 구체화한다.
> "두 영역의 렌더링 결과가 같다"는 강조 표시를 뺀 두 영역의 DOM을 각각 Virtual DOM 트리로 변환해 비교했을 때 같다는 뜻이다. 공백 텍스트 노드와 주석 노드는 비교에서 빠진다.
> 비고 열의 "삭제됨"은 번호를 유지하기 위해 남긴 행이다.

### 5.1 엔진: Mini React 핵심 동작

| ------ | ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| FR-E01 | 항상 (Ubiquitous) | 시스템은 영역 컨테이너 아래의 DOM 트리를 태그, 속성, 자식(텍스트 노드 포함)을 가진 Virtual DOM 트리로 변환해야 한다.                         | 샘플 HTML 코드의 DOM 트리를 변환해 노드마다 태그, 속성, 텍스트, 자식 순서가 같은지 단위 테스트로 확인                       |                              |
| FR-E02 | 항상 (Ubiquitous) | 시스템이 Virtual DOM 트리로 다시 만든 DOM은 원래 DOM과 같아야 한다.                                                                          | 원래 DOM에서 공백 텍스트 노드와 주석 노드를 뺀 뒤, DOM → Virtual DOM 트리 → DOM 왕복 결과와 `isEqualNode`로 같은지 확인 | ADR-007 승인 시 수정         |

| FR-E04 | 이벤트 (When)     | Diff 결과가 주어지면, 시스템은 바뀐 노드만 실제 DOM에 반영해야 하며 전체를 다시 그리면 안 된다.                                              | Patch 전후로 바뀌지 않은 노드가 같은 DOM 객체(`===`)로 유지되는지 확인                                                    |                              |
| FR-E05 | 항상 (Ubiquitous) | 시스템은 입력된 HTML 문자열이 아니라 브라우저가 파싱한 DOM 트리를 Virtual DOM 트리로 변환해야 한다.                                          | `<table><tr><td>A</td></tr></table>`을 변환해 Virtual DOM 트리에 `tbody`가 들어 있는지 확인                             | 엣지 케이스                  |
| FR-E06 | 항상 (Ubiquitous) | 시스템은 DOM 트리를 Virtual DOM 트리로 변환할 때 공백과 줄바꿈만 있는 텍스트 노드를 넣지 않아야 한다.                                        | `<ul>`과 `<li>A</li>` 사이에 줄바꿈을 넣은 HTML을 변환해 `ul`의 자식이 `li` 하나뿐인지 확인                         | 엣지 케이스 (추후 조사 필요). ADR-007 승인 시 수정 |
| FR-E07 | 항상 (Ubiquitous) | 시스템은 DOM 트리를 Virtual DOM 트리로 변환할 때 주석 노드를 넣지 않아야 한다.                                                               | `<div><!-- 메모 --><p>A</p></div>`를 변환해 `div`의 자식이 `p` 하나뿐인지 확인                                        | ADR-007 승인 시 수정         |
| FR-E08 | 항상 (Ubiquitous) | 시스템은 브라우저가 파싱한 모든 HTML 코드(빈 문자열 포함)를 Virtual DOM 트리로 변환할 수 있어야 하며, 별도의 유효성 검사를 하지 않아야 한다. | 닫히지 않은 태그, 잘못된 중첩, 빈 문자열을 넣어도 오류 없이 변환되는지 확인                                                 | FR-W09 삭제 대체             |
| FR-E09 | 이벤트 (When)     | 수정한 HTML 코드가 빈 문자열일 때 사용자가 Patch 버튼을 누르면, 시스템은 실제 영역의 모든 노드를 삭제해야 한다.                              | 빈 문자열로 Patch한 뒤 실제 영역에 노드가 없고 두 영역의 렌더링 결과가 같은지 확인                                          | 빈 문자열 Patch 허용         |

```html

    <li>장보기</li>
    <li>운동하기</li>
  </ul>
  <button type="button">추가</button>
</div>
```

## 6. 설계로 넘기는 항목

- 트리 순회 방식 (재귀 / 반복문 스택 / Fiber)과 근거 → ADR로 기록 (임동호 014에서 이동)
- 뒤로가기, 앞으로가기를 기록의 상태 전체로 바꿀지, Diff와 Patch를 거칠지
- 자식 비교 방식 (key 없이 인덱스 기준으로 비교할지, 순서가 바뀐 경우를 삭제 + 추가로 볼지)
- Patch 도중 오류가 나서 실제 영역이 일부만 바뀐 경우의 처리
- State History 기록 개수 상한
