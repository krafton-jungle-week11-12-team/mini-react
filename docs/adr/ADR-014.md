# ADR-014: 입력한 HTML 코드로 만든 Virtual DOM 트리는 레이아웃용 허용 목록으로 걸러, 목록 밖의 요소 노드와 속성을 빼고 반영한다

- 상태: 제안됨
- 관리 범위: mini-react 저장소 (docs/adr)

## 개요

사용자가 테스트 영역에 입력한 HTML 코드 중 무엇을 화면에 반영할지에 대한 결정이에요. 이 글을 읽으면 왜 스크립트를 막는지, 왜 차단 목록이 아니라 허용 목록을 쓰는지, 목록 밖의 입력이 들어오면 화면이 어떻게 되는지 알 수 있어요.

## 맥락

요구사항 2.2는 "스크립트 실행 차단"을 범위에서 빼고 "(협의 필요)"로 남겼어요. 7절에도 "스크립트 실행 정책 확정"이 추후 논의로 남아 있어요.

[ADR-013](ADR-013.md)(제안됨) 뒤로 두 영역은 `toDOM`의 `createElement`로 그려요. 이렇게 만든 `<script>`는 문서에 붙을 때 실행되고, 이벤트 속성(`onerror` 등)도 실행돼요. 그래서 `<script>` 하나가 두 영역에서 각각 실행돼요.

스크립트 말고도 검증 페이지를 망가뜨리는 입력이 있어요.

- 페이지 이동: `<form>` 안의 `<button>`을 누르면 페이지가 새로 고쳐져 State History가 사라져요. `<a href>`를 누르면 다른 페이지로 가요.
- 페이지 전체에 영향: `<style>`, `<link>`는 두 영역 밖의 화면까지 바꿔요. `<base>`는 페이지의 상대 경로를, `<meta http-equiv="refresh">`는 페이지 위치를 바꿔요.
- DOM clobbering: `<img name="createElement">`를 넣으면 `document.createElement`가 이 요소 노드로 덮여, 다음 `toDOM`부터 동작하지 않아요.
- 다른 문서 끼워 넣기: `iframe`, `object`, `embed`, `svg`, `math`는 안에서 스크립트를 실행할 수 있어요. `svg`, `math`는 [Virtual DOM 설계](../design/phase1/vdom.md)에서 지원하지 않아요.
- 외부 요청: `<img src>`, `style="background: url(...)"`은 입력할 때마다 외부로 요청을 보내요.
- 화면 덮기: `style="position: fixed"`는 영역 밖의 버튼까지 덮을 수 있어요.

## 고려한 선택지

### 선택지 A: 막지 않는다 (지금)

- 장점: 할 일이 없어요. 사용자가 무엇이든 넣어 볼 수 있어요.
- 단점: 위 입력 하나로 페이지가 이동하거나 엔진이 멈춰요. 이력서와 포트폴리오에 넣을 결과물로는 부족해요.

### 선택지 B: 차단 목록 (위험한 것만 뺀다)

- 장점: 레이아웃 밖의 요소 노드도 넣어 볼 수 있어요.
- 단점: 위험한 요소 노드와 속성을 빠짐없이 적어야 해요. 하나라도 빠뜨리면 뚫려요.

### 선택지 C: 허용 목록 (레이아웃용 요소 노드와 속성만 남긴다)

- 장점: 목록에 없는 것은 모두 빠져서 새로 알게 된 위험도 처음부터 막혀요. 과제의 목적인 레이아웃 변경과 Diff 확인에는 충분해요.
- 단점: `img`, `a`처럼 흔한 요소 노드도 빠져요. 허용 목록을 관리해야 해요.

목록 밖의 입력을 어떻게 다룰지도 비교했어요.

- 빼고 반영한다: 나머지 입력은 그대로 Patch할 수 있어요. 뺀 것을 문구로 알려 줘요.
- Patch를 막는다: 무엇이 빠졌는지 헷갈리지 않지만, 붙여 넣은 HTML 코드를 하나씩 고쳐야 해요.

## 결정

입력창의 HTML 코드로 만든 Virtual DOM 트리는 허용 목록으로 걸러, 목록 밖의 요소 노드와 속성을 빼고 반영한다.

1. 거르는 곳은 검증 페이지의 파싱 한 곳이다. 버튼 판단과 Patch가 같은 함수로 거른다. 엔진 모듈(`toVNode`, `diff`, `patch`, `toDOM`)은 고치지 않는다.
2. 허용 목록 밖의 요소 노드는 자식까지 통째로 뺀다. 텍스트 노드와 주석 노드는 그대로 둔다.
3. 허용 목록 밖의 속성은 그 속성만 뺀다. `on`으로 시작하는 이벤트 속성, `name`, `src`, `href`는 목록에 없다. `aria-`, `data-`로 시작하는 속성과 `key`는 허용한다.
4. `style` 속성은 허용한다. 값에 `url(`, `image(`, `image-set(`, 역슬래시가 있으면 속성을 통째로 뺀다.
5. 두 렌더링 결과 박스에 CSS `contain: paint`를 걸어, `position: fixed` 같은 요소 노드가 박스 밖을 덮지 못하게 한다.
6. 뺀 것이 있으면 입력 중에는 "허용하지 않는 요소·속성은 빼고 반영해요: `<script>`, onclick" 문구를 보여 주고, Patch 뒤에는 요약 문구 뒤에 같은 문구를 붙인다.
7. State History의 `html`에는 입력 원문을 그대로 저장한다. `vdom`에는 거른 트리를 저장한다.

허용 목록은 [입력 걸러내기 설계](../design/phase1/sanitize.md)에 둔다.

## 근거

C는 목록에 있는 것만 남기므로 B처럼 빠뜨린 위험이 생기지 않아요. 과제는 "사용자가 테스트 영역의 샘플 HTML 코드를 자유롭게 수정"하는 것이고, 확인할 것은 Virtual DOM, Diff, Patch예요. 레이아웃용 요소 노드와 속성만으로 다섯 가지 Diff 경우(추가, 삭제, 교체, 속성, 텍스트)와 key 비교를 모두 확인할 수 있어요.

거르는 곳을 파싱 한 곳에 두면 버튼 판단, Patch, 기록 이동이 모두 같은 트리를 써요. 엔진 모듈은 받은 트리를 그대로 다뤄 Phase 2에서도 그대로 쓸 수 있어요.

빼고 반영하는 쪽은 붙여 넣은 HTML 코드에 허용하지 않는 속성 하나만 있어도 Patch를 할 수 있어요. 뺀 것은 문구로 알려 줘서 왜 화면에 안 보이는지 알 수 있어요.

## 예상되는 결과

- 긍정적 영향: 입력한 HTML 코드로는 스크립트가 실행되지 않고, 페이지가 이동하지 않으며, 외부 요청이 가지 않아요. 2026-11-11 Chrome에서 `<script>`, `onmouseover`, `<img onerror>`, `<form>`, `<img name="createElement">`를 넣고 Patch, 뒤로가기, 앞으로가기를 해도 스크립트가 한 번도 실행되지 않았고, 다음 Patch도 정상이었어요.
- 긍정적 영향: 요구사항 2.2와 7절의 스크립트 실행 정책 협의가 끝나요.
- 부정적 영향 / 리스크: `img`, `a`, `form`, `svg`처럼 레이아웃 밖의 요소 노드는 화면에 넣어 볼 수 없어요.
- 부정적 영향 / 리스크: 입력창의 HTML 코드와 화면이 달라요. 뺀 요소 노드는 HTML 코드에 남지만 화면에는 없어요. 문구로 알려 주는 것으로 대신해요.
- 부정적 영향 / 리스크: 처음 로드할 때 실제 영역은 샘플 HTML 코드를 `innerHTML`로 넣어서 거르지 않아요. 샘플 HTML 코드가 허용 목록 안에 있어서 문제는 없어요. 샘플을 바꾸면 허용 목록 안에 있는지 확인해야 해요.
