# 문서 검증

입력: `$ARGUMENTS`

이 스킬은 읽고 보고만 해요. 요구사항, 설계, ADR 문서를 고치지 않아요. 고칠 내용은 보고 표에 적고, 고치는 일은 사용자나 `/design-doc`이 해요.

## 0. 입력 확인

입력은 두 가지 중 하나예요.

- **Phase 검증**: 첫 단어가 Phase예요. `.claude/skills/README.md`의 "Phase 인자" 절대로 읽어요. 그 Phase의 요구사항, 설계, 관련 ADR 문서를 모두 검증해요.
- **문서 검증**: `.md`로 끝나는 경로가 하나 이상 와요. (예: `docs/adr/ADR-010.md`, `docs/design/phase2/use-state.md docs/design/phase2/deps.md`) 그 문서만 검증해요.

입력이 비었으면 AskUserQuestion으로 Phase와 문서 중 무엇을 검증할지 물어요. 준 경로에 파일이 없으면 멈추고 알려요.

## 1. 검증 대상 확인

문서 종류는 경로로 정해요.

| 경로 | 종류 |
| ---- | ---- |
| `docs/requirements/**` | 요구사항 |
| `docs/design/**` (`TEMPLATE.md` 빼고) | 설계 |
| `docs/adr/ADR-*.md` | ADR |
| `docs/testcase/**` (`TEMPLATE.md` 빼고) | 테스트 케이스 |
| `.claude/skills/*/SKILL.md` | 스킬 |
| 그 밖의 `.md` 문서 | 기타 |

기타 문서도 빠뜨리지 않고 3.6 "공통 검증"으로 검증해요.

Phase 검증이면 아래를 대상으로 해요.

- 요구사항: `docs/requirements/<phase>/` 아래 문서 전부
- 설계: README "Phase 인자" 절의 설계 문서 위치 아래 문서 전부
- 테스트 케이스: `docs/testcase/<phase>/` 아래 문서 전부 (없으면 건너뛰어요)
- ADR: 위 문서가 링크하거나 비고에 적은 ADR, 그리고 "영향받는 요구사항" 표에 이 Phase 요구사항 ID가 있는 ADR

대상 목록을 아래 형식으로 보여 주고 바로 2단계로 넘어가요.

| 문서 | 종류 | 상태 |
| ---- | ---- | ---- |

## 2. 읽을 문서

검증 전에 아래를 읽어요. 대상에 없는 종류의 기준 문서는 건너뛰어요.

1. 1단계의 대상 문서 전부
2. 기준 문서
   - 요구사항: `.claude/skills/design-doc/SKILL.md` 1단계 "요구사항 문서 완성 확인"
   - 설계: `docs/design/TEMPLATE.md`, `.claude/skills/design-doc/SKILL.md` 4단계 "템플릿 형식 지키기"와 5단계 "전체 연결성 검증"
   - ADR: `docs/adr/TEMPLATE.md`, `.claude/rules/docs-writing.md`의 "ADR과 요구사항이 충돌할 때"
   - 테스트 케이스: `docs/testcase/TEMPLATE.md`
   - 스킬: `.claude/skills/TEMPLATE.md`, `.claude/rules/skill-writing.md`, `.claude/skills/README.md`
   - 기타: 문서와 같은 폴더나 위 폴더에서 가장 가까운 `TEMPLATE.md`. 없으면 기준 템플릿 없이 공통 검증만 해요.
   - 모든 종류: `docs/technical-writing-principles.md`
3. 대상 문서가 가리키는 문서 (요구사항, 설계, ADR). 문서 검증이어도 참조가 맞는지 보려면 읽어요.
4. `src/` — 설계 문서의 타입과 함수 시그니처가 실제 코드와 다른지 볼 때만 읽어요.

## 3. 검증

항목마다 문제가 없어도 결과 표에 한 줄을 남겨요. 문서 검증일 때는 "문서 하나" 항목만 하고, "Phase 전체" 항목은 건너뛰어요.

### 3.1 요구사항

- 문서 하나: `design-doc` 1단계 확인 항목 1~6을 따라요. (안내 주석, 자리표시자, 필수 섹션, 기능 요구사항 표, 헤더 표, 승인 대기 ADR)
- 문서 하나: 요구사항 ID가 문서 안에서 겹치지 않아요. "삭제됨" 행의 번호를 다른 요구사항이 다시 쓰지 않아요.

### 3.2 설계

- 문서 하나: `design-doc` 5단계 9번 "템플릿 형식"을 따라요. "이번에 쓰거나 고친 문서" 대신 대상 설계 문서 전부에 적용해요. 작성자 `[이름]`, 관련 이슈 `#[번호]`는 문제가 아니라 "비워 둔 값"으로 따로 적어요.
- 문서 하나: `design-doc` 5단계 2번(없는 ID 참조), 7번(ADR 참조)을 따라요.
- Phase 전체: `design-doc` 5단계 1번(커버리지), 3번(설계로 넘기는 항목), 4번(입출력 연결), 5번(타입·인터페이스 일치), 6번(동작 흐름 따라가기)을 따라요.

### 3.3 ADR

- 문서 하나: `docs/adr/TEMPLATE.md` 형식을 따라요.
  - 파일 이름 `ADR-<세 자리 번호>.md`, 제목 `# ADR-<번호>: <결정 문장>`. 제목이 주제가 아니라 결정이에요.
  - 머리 정보 `- 상태:`, `- 관리 범위:`. 상태는 제안됨, 승인됨, 기각됨 중 하나예요.
  - `##` 섹션 이름과 순서: 개요, 맥락, 고려한 선택지, 결정, 근거, 예상되는 결과, 영향받는 요구사항, 관련 참조 문서
  - 남은 주석(`<!--`)과 자리표시자(`[주제]`, `[이름]`, `[장점]`, `FR-[ID]` 등). 백틱 안의 코드와 링크는 빼고 찾아요.
- 문서 하나: "영향받는 요구사항" 표와 요구사항 문서가 `docs-writing.md` 절차대로 맞아요.
  - 제안됨: 표의 요구사항 행 비고에 `ADR-<번호> 승인 시 수정`이 있어요.
  - 승인됨: 요구사항 본문이 표의 "바뀌는 내용"대로 바뀌었고, 비고의 표시가 지워졌어요.
  - 기각됨: 비고의 표시가 지워졌어요.
  - 표의 ID가 실제 요구사항 문서에 있어요.

### 3.4 스킬

스킬은 문서 검증으로만 검증해요. Phase 검증 대상에는 넣지 않아요.

- 문서 하나: `.claude/skills/TEMPLATE.md` 형식을 따라요.
  - 머리 정보에 `name`, `description`이 있고, `name`이 폴더 이름과 같은 kebab-case예요. 호출 방식 줄이 템플릿 주석의 세 가지 중 하나예요.
  - `##` 절이 템플릿의 단계 순서(확인 → 읽기 → 계획 확인 → 작성 → 검증 → 보고)를 따라요. 빠진 단계는 있어도 되지만 순서가 바뀌면 안 돼요.
  - 남은 주석(`<!--`)과 자리표시자(`[스킬 이름]`, `[항목]`, `[대상]` 등). 백틱 안의 코드와 링크는 빼고 찾아요.
- 문서 하나: `.claude/rules/skill-writing.md`의 "쓸 때" 규칙을 따라요. 고치는 파일과 읽고 보고만 하는 파일이 앞쪽에 있고, 결과 전 `doc-check` 검수 단계가 있어요. (`doc-check` 자신은 빼요.)
- 문서 하나: 본문에 적은 경로가 실제로 있고, 가리키는 다른 스킬의 단계 번호와 절 이름이 실제와 맞아요.
- 문서 하나: `.claude/skills/README.md` "스킬" 표에 이 스킬 행이 있고, 명령어와 고치는 파일이 SKILL.md와 같아요.

### 3.5 테스트 케이스

- 문서 하나: `docs/testcase/TEMPLATE.md` 형식을 따라요. 제목, 머리 정보, `##` 섹션 이름과 순서, 표의 열 이름, 남은 주석(`<!--`)과 자리표시자를 `grep`으로 확인해요.
- 문서 하나: 관련 요구사항 문서의 요구사항 ID("삭제됨" 빼고)가 모두 "테스트 케이스" 표나 "테스트하지 않는 요구사항"에 있어요.
- 문서 하나: 적은 요구사항 ID가 실제 요구사항 문서에 있고, 테스트 케이스 ID가 템플릿 형식이며 겹치지 않아요.
- 문서 하나: 테스트 파일 칸에 적은 파일이 실제로 있어요.
- `docs/testcase/TEMPLATE.md`가 없으면 형식 검사는 "확인 불가"로 적고 나머지만 해요.

### 3.6 공통 검증

종류와 상관없이 모든 대상 문서에 해요. 기타 문서는 이것만 해요.

- 기준 템플릿이 있으면 제목, 머리 정보, `##` 섹션 이름과 순서가 템플릿과 같아요.
- 남은 템플릿 주석(`<!--`)과 자리표시자(`[이름]`, `[항목]`처럼 템플릿 그대로인 칸)가 없어요. 백틱 안의 코드와 링크는 빼고 찾아요.
- 적은 요구사항 ID(`FR-<영문><숫자>`), ADR 번호가 실제 문서에 있어요.
- 문장이 `docs/technical-writing-principles.md`에 크게 어긋나지 않아요. (예: 가치를 먼저 쓰지 않음, 속성 설명에 형식·예시가 없음) 어긋난 곳은 "문제"가 아니라 "제안"으로 적어요.

### 3.7 문서 사이

- 문서 하나: 문서 안의 상대 링크가 실제 파일을 가리켜요. (`ls`로 확인)
- Phase 전체: 요구사항 비고의 `ADR-<번호> 승인 시 수정` 표시마다 그 ADR이 있고, 상태가 제안됨이고, "영향받는 요구사항" 표에 그 ID가 있어요. 표시는 있는데 ADR 표에 없거나, 그 반대인 경우를 적어요.

## 4. 마지막 보고

검증 결과는 아래 형식으로 보고해요. 문제 위치는 `파일:줄` 링크로 적어요.

| # | 문서 | 항목 | 결과 (통과 / 문제 / 확인 불가) | 문제 위치 | 고칠 내용 | 고칠 곳 (요구사항 / 설계 / ADR / 테스트 케이스 / 스킬 / 기타) |
| - | ---- | ---- | ------------------------------ | --------- | --------- | -------------------------------------------------------------- |

표 아래에 아래를 적어요.

- 요약: 문제 수와 가장 먼저 고칠 것 한 가지
- 비워 둔 값: 작성자 `[이름]`, 관련 이슈 `#[번호]`가 남은 문서
- 사용자가 정해야 할 것: ADR이 필요한 결정, 요구사항과 충돌하는 부분
- 요구사항을 고쳐야 하는 문제는 `.claude/rules/docs-writing.md`의 ADR 절차나 `/design-doc` 7단계 "요구사항 반영"으로 처리하라고 안내해요.
