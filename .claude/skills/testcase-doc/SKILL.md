# 테스트 케이스 문서 작성

입력: `$ARGUMENTS`

이 스킬이 고치는 파일은 `docs/testcase/` 아래 문서예요. 요구사항, 설계, ADR 문서와 `src/` 코드는 읽고 보고만 해요. 테스트 코드는 쓰지 않아요.

## 0. 입력 확인

- 첫 단어는 Phase예요. `.claude/skills/README.md`의 "Phase 인자" 절대로 읽어요.
- 둘째 단어부터는 대상이에요. 요구사항 문서 경로(예: `docs/requirements/phase2/use-memo_requirement.md`)나 요구사항 ID(예: `FR-M01 FR-M02`)를 받아요. 없으면 그 Phase의 요구사항 문서 전체를 대상으로 해요.
- 준 경로나 ID가 요구사항 문서에 없으면 멈추고 알려요.

## 1. 시작 전 확인

### 요구사항 완성 확인

`.claude/skills/design-doc/SKILL.md` 1단계 "요구사항 문서 완성 확인"을 따라요. 결과 표, 멈추는 조건, AskUserQuestion 선택지도 그대로 따라요. 단, "완성된 문서만 설계"는 "완성된 문서만 테스트 케이스 작성"으로 읽어요.

### 템플릿 확인

`docs/testcase/TEMPLATE.md`가 있는지 확인해요.

- 있으면 2단계로 넘어가요.
- 없으면 템플릿을 먼저 만들어요.
  1. `docs/design/TEMPLATE.md`와 `docs/adr/TEMPLATE.md`의 모양(맨 위 작성 규칙 주석, 머리 정보, 섹션 안내 주석, 표)을 본떠요.
  2. 아래 내용이 들어가야 해요.
     - 머리 정보: 상태, 작성자, 관련 요구사항 문서 링크, 관련 설계 문서 링크
     - 개요: "이 문서를 읽으면 ~을 할 수 있어요." 꼴
     - 다루는 요구사항: 요구사항 ID, 요약, 테스트 케이스 ID
     - 테스트 환경: 단위 테스트(vitest + jsdom, `npm test`)와 검증 페이지(`npm run dev`)
     - 테스트 케이스: 테스트 케이스 ID, 요구사항 ID, 종류(단위 테스트 / 검증 페이지), 준비, 입력·절차, 기대 결과, 테스트 파일
     - 추가 테스트 케이스: 요구사항 밖에서 사용자가 추가하기로 한 케이스와 근거
     - 테스트하지 않는 요구사항: ID와 이유. 없으면 "없음"
     - 관련 문서
  3. 테스트 케이스 ID 형식을 정해 작성 규칙 주석에 적어요. (예: `FR-E01`의 첫 케이스는 `TC-E01-01`)
  4. 만든 템플릿을 보여 주고 AskUserQuestion으로 확인받아요. 사용자가 고치라고 하면 고쳐 다시 보여 줘요.

## 2. 읽을 문서

작성 전에 아래를 모두 읽어요.

1. 대상 요구사항 문서 — 3절 용어, 4절 동작 흐름, 5절 기능 요구사항과 확인 방법(초안), 6절 결정된 항목
2. `docs/testcase/TEMPLATE.md` — 결과물 형식. 4단계는 이 형식을 그대로 따라요.
3. `docs/technical-writing-principles.md` — 문장 기준
4. 이 Phase의 설계 문서 (위치는 README "Phase 인자" 절) — 인터페이스, 동작 방식, 경계 케이스, 검증 방법
5. `docs/adr/` — 요구사항 비고에 `ADR-<번호> 승인 시 수정`이 붙은 ADR
6. `src/**/*.test.ts` — 이미 있는 테스트. 같은 확인을 하는 테스트가 있으면 테스트 파일 칸에 적어요.
7. 이미 있는 `docs/testcase/<phase>/` 문서

## 3. 계획 확인

- 요구사항 문서 하나에 테스트 케이스 문서 하나를 둬요. 경로는 `docs/testcase/<phase>/<요구사항 문서 파일 이름>`이에요. (예: `docs/testcase/phase2/use-memo_requirement.md`)
- 쓰기 전에 아래 표를 보여 주고 확인을 받아요. 이미 있는 문서를 고치는 경우도 적어요.

| 테스트 케이스 문서 경로 | 요구사항 문서 | 다루는 요구사항 ID | 새로 작성 / 수정 |
| ----------------------- | ------------- | ------------------ | ---------------- |

## 4. 작성

### 형식 지키기

새 문서는 `docs/testcase/TEMPLATE.md`를 복사해서 시작하고, 형식을 바꾸지 않고 칸만 채워요. 템플릿 주석과 자리표시자는 다 쓴 뒤 모두 지워요. 작성자는 모르면 `[이름]`으로 남기고 마지막 보고에서 알려요.

### 기본 테스트 케이스

요구사항에서 바로 나오는 케이스예요. 사용자에게 묻지 않고 써요.

- 비고가 "삭제됨"이 아닌 요구사항마다 테스트 케이스를 하나 이상 둬요.
- 확인 방법(초안)을 실제로 돌릴 수 있게 구체화해요. 입력은 실제 값(HTML 문자열, 호출 코드)으로, 기대 결과는 확인할 값으로 써요. "잘 동작한다"처럼 확인할 수 없는 말은 쓰지 않아요.
- 요구사항 유형을 따라요. 이벤트(When)는 그 이벤트를 일으키는 절차를, 오류(If)는 오류 조건과 기대하는 처리를, 상태(While)는 그 상태를 만드는 준비를 적어요.
- 요구사항과 설계에 없는 동작을 기대 결과로 만들지 않아요.
- 확인 방법대로 해도 기대 결과가 나오지 않거나, 확인할 수 없는 요구사항은 "테스트하지 않는 요구사항"에 이유와 함께 적고 마지막 보고에서 알려요. 요구사항 문서는 고치지 않아요.
- `ADR-<번호> 승인 시 수정`이 붙은 요구사항의 케이스는 바뀔 수 있다고 비고에 적어요.

### 추가 테스트 케이스 제안

기본 케이스를 다 쓴 뒤, 요구사항에는 없지만 있으면 좋을 케이스를 모아요.

- 설계 문서 "경계 케이스" 중 기본 케이스가 다루지 않는 것
- 빈 값, 경계 값, 같은 동작 반복, 순서가 바뀐 입력, 오류 뒤 상태처럼 요구사항이 말하지 않는 경우
- 두 모듈이 이어지는 곳 (요구사항 4절 흐름에서 앞 단계 결과를 다음 단계가 받는 곳)

모은 케이스를 아래 표로 보여 줘요.

| # | 제안 케이스 | 입력·절차 | 기대 결과 | 근거 (설계 문서 경계 케이스 / 흐름 / 기타) | 관련 요구사항 |
| - | ----------- | --------- | --------- | ------------------------------------------ | ------------- |

그다음 반드시 AskUserQuestion으로 "이 테스트 케이스도 추가할까요?"라고 물어요. 제안이 없으면 "추가로 제안할 테스트 케이스가 없어요"라고 알리고 넘어가요.

- **모두 추가** (추천): 표의 케이스를 전부 "추가 테스트 케이스"에 넣어요.
- **일부만 추가**: 번호를 받아 그 케이스만 넣어요.
- **추가하지 않음**: 넣지 않아요.

추가한 케이스의 기대 결과가 요구사항에 없는 새 동작이면, 마지막 보고의 "요구사항에 더할 것"에 적어요. 요구사항 문서는 고치지 않아요.

## 5. 검증

이번에 쓰거나 고친 테스트 케이스 문서를 대상으로 아래를 확인해요.

1. **커버리지**: 대상 요구사항 ID가 모두 "테스트 케이스" 표나 "테스트하지 않는 요구사항"에 있어요.
2. **없는 ID 참조**: 문서에 적은 요구사항 ID가 실제 요구사항 문서에 있어요.
3. **테스트 케이스 ID**: 템플릿이 정한 형식이고, 문서 안에서 겹치지 않아요.
4. **테스트 파일**: 테스트 파일 칸에 적은 파일이 실제로 있어요. (`ls`로 확인)
5. **문서 검수**: `.claude/skills/doc-check/SKILL.md`를 읽고, 이번에 쓰거나 고친 문서 경로를 입력으로 그 절차대로 검수해요.

검증 결과는 아래 형식으로 보고해요.

| # | 항목 | 결과 | 문제 위치 | 고칠 내용 |
| - | ---- | ---- | --------- | --------- |

- 이번에 쓴 문서의 문제는 바로 고치고 다시 검증해요.
- 요구사항, 설계, ADR 문서를 고쳐야 하는 문제는 고치지 않고 보고만 해요.

## 6. 마지막 보고

- 작성·수정한 파일 목록 (템플릿을 만들었으면 함께)
- 검증 결과 표 (doc-check 검수 결과 포함)
- 추가한 테스트 케이스 수와 추가하지 않은 제안
- 테스트하지 않는 요구사항과 이유
- 요구사항에 더할 것: 추가 케이스에서 나온 새 동작, 틀린 확인 방법. 없으면 "없음"
- 사용자가 정해야 할 것 (비워 둔 작성자, 승인 대기 ADR에 걸린 케이스)
