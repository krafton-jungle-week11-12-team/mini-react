# ADR-004: 테스트 영역 렌더링 결과는 HTML을 파싱한 DOM으로 만든다

- 상태: 승인됨
- 관리 범위: mini-react 저장소 (docs/adr)

## 개요

테스트 영역의 렌더링 결과를 무엇으로 만들지에 대한 결정이에요. 이 글을 읽으면 왜 Virtual DOM 트리를 변환한 DOM 대신 HTML을 파싱한 DOM을 쓰는지 알 수 있어요.

## 맥락

요구사항 초안에서 테스트 영역을 만드는 방법이 시점마다 달랐어요. 페이지 로드 때는 Virtual DOM 트리를 변환한 DOM을, Patch 때는 HTML 코드를 파싱한 DOM을 썼어요. 하나로 통일해야 했어요.

## 고려한 선택지

검토한 대안과 장단점은 다음과 같아요.

### 선택지 A: 항상 Virtual DOM 트리 → DOM 변환

- 장점: 로드와 Patch의 경로가 같아요.
- 단점: 변환이 불완전하면 두 영역이 처음부터 달라지고, 변환 버그가 양쪽에 똑같이 생겨 드러나지 않아요.

### 선택지 B: 항상 HTML 코드를 파싱한 DOM

- 장점: 두 영역이 같은 상태에서 시작해요. 테스트 영역이 엔진을 거치지 않아 비교 기준이 돼요.
- 단점: Virtual DOM → DOM 변환은 화면에서 확인할 수 없어요.

## 결정

테스트 영역의 렌더링 결과는 로드, Patch, 기록 이동 모두 HTML 코드를 브라우저가 파싱한 DOM으로 만든다. Virtual DOM → DOM 변환은 Patch가 새 노드를 만들 때만 쓴다.

## 근거

Patch는 이미 파싱한 DOM을 쓰고 있어서, 변환 함수로 테스트 영역을 만드는 곳은 로드뿐이었어요. 로드 때 변환이 불완전하면 두 영역의 차이가 첫 Patch에서 사용자의 수정처럼 실제 영역에 반영돼요. B를 고르면 이 문제가 생기지 않아요.

## 예상되는 결과

이 결정으로 예상되는 영향은 다음과 같아요.

- 긍정적 영향: Patch 후 두 영역이 다르면 엔진이 틀렸다는 뜻이 돼요.
- 부정적 영향 / 리스크: Virtual DOM → DOM 변환은 FR-E02 단위 테스트로만 검증해요.
