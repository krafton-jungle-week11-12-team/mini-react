# ADR-011: key Diff는 뒤로 돌아간 노드만 이동으로 보고, Patch는 같은 노드를 insertBefore로 옮긴다

- 상태: 제안됨
- 관리 범위: mini-react 저장소 (docs/adr)

## 개요

Phase 2의 key 기반 Diff에서 순서가 바뀐 노드를 어떻게 처리할지에 대한 결정이에요. 이 글을 읽으면 왜 이동(MOVE)을 삭제 + 추가로 대신하지 않는지, 어떤 노드를 이동한 것으로 보는지, Patch가 노드를 어떻게 옮기는지 알 수 있어요.

## 맥락

[ADR-002](ADR-002.md)는 Phase 2에서 자식 목록을 key로 짝짓기로 했어요(선택지 B). key로 짝지으면 Phase 1에는 없던 경우가 생겨요. **같은 항목인데 자리가 바뀐** 경우예요.

```text
이전: [A, B, C]     새: [C, A, B]
key로 짝지음: A↔A, B↔B, C↔C → 내용은 모두 같고 순서만 다름
```

지금 Patch 명령(`CREATE`, `REMOVE`, `REPLACE`, `TEXT`, `UPDATE`)은 모두 "그 자리에서" 무언가를 해요. Diff 결과도 "i번째 칸 = 부모의 i번째 자식"이라는 약속 위에 있어요. 그래서 순서 변경을 어떻게 표현하고, 어떤 노드를 옮길지 정해야 해요.

key를 쓰는 이유는 항목의 DOM 노드를 지키는 것이에요. 체크 상태, input에 친 글자, 포커스는 DOM 노드에 남아 있어서, 노드를 버리고 새로 만들면 사라져요. ([#122](https://github.com/orgs/krafton-jungle-week11-12-team/discussions/122))

이 ADR은 순서 변경 처리만 다뤄요. key 규칙과 key가 없는 노드(공백 · 주석 노드 포함)의 처리는 ADR-002에 따라 Phase 2 설계에서 정해요.

## 고려한 선택지

### 선택지 A: 이동을 삭제 + 추가로 대신한다

자리가 바뀐 노드는 이전 자리에서 `REMOVE`하고 새 자리에 `CREATE`해요.

- 장점: 새 Patch 명령이 필요 없어요.
- 단점: DOM 노드를 버리고 새로 만들어서 체크 상태, 입력값, 포커스가 사라져요. key로 노드를 지키려던 목적이 없어져요.

### 선택지 B: key가 같은데 인덱스가 달라진 노드를 모두 이동으로 본다

- 장점: 판단이 가장 단순해요. 인덱스 두 개만 비교하면 돼요.
- 단점: 추가나 삭제가 하나만 있어도 뒤 노드의 인덱스가 모두 밀려서, 움직이지 않은 노드까지 이동으로 잡혀요.

  ```text
  [A, B, C] → [X, A, B, C]   X만 추가했는데 A, B, C가 모두 이동으로 잡힘
  ```

### 선택지 C: 뒤로 돌아간 노드만 이동으로 본다 (React 방식)

새 목록을 왼쪽부터 보면서, 지금까지 그대로 둔 노드 중 이전 위치가 가장 뒤인 것(`lastPlacedIndex`)을 기억해요. 지금 노드의 이전 위치가 그보다 앞이면 이동, 아니면 그대로 둬요.

- 장점: 왼쪽부터 한 번만 훑으면 되고, 판단이 `if` 하나예요. 끝에 추가, 중간 삭제, 한 항목을 뒤로 옮기기처럼 흔한 경우는 이동 횟수가 최소예요.
- 단점: 맨 뒤 노드를 맨 앞으로 옮기면, 그 노드 하나 대신 나머지가 모두 이동으로 잡혀요. 화면 결과는 맞고 이동 횟수만 늘어요.

  ```text
  [A, B, C] → [C, A, B]   C 하나만 옮기면 되는데 A, B가 이동으로 잡힘
  ```

### 선택지 D: 가장 긴 증가 부분 수열(LIS)에 들지 않는 노드만 이동으로 본다 (Vue 3 방식)

- 장점: 이동 횟수가 항상 최소예요.
- 단점: LIS 계산이 더 필요해 구현이 가장 어려워요. ADR-002에서 이미 쓰지 않기로 했어요.

## 결정

자리가 바뀐 노드는 지우고 새로 만들지 않고, 같은 DOM 노드를 옮긴다. 이동 여부는 선택지 C(React 방식)로 판단한다.

1. Diff는 새 목록을 왼쪽부터 보며, 이전 위치가 `lastPlacedIndex`보다 앞인 노드를 이동으로 표시한다. 이전 목록에 없는 노드는 추가, 새 목록에 없는 노드는 삭제로 표시한다.
2. 이동은 내용 변경(`UPDATE`, `TEXT`)과 함께 일어날 수 있다. 한 노드가 이동과 내용 변경을 모두 가질 수 있게 표현한다.
3. Patch는 이동할 노드를 `insertBefore`로 옮긴다. 기준 노드는 새 목록에서 그 노드 바로 뒤에 올 노드이고, 맨 끝이면 `null`이다.
4. 이동한 노드는 새로 만들지 않고, 이전 DOM 노드 객체를 그대로 쓴다.

## 근거

- **삭제 + 추가(A)는 key의 목적과 맞지 않아요.** key는 항목의 DOM 노드를 지키려고 쓰는데, A는 순서가 바뀔 때마다 그 노드를 버려요. 그래서 이동 명령이 따로 필요해요.
- **`insertBefore`로 옮기면 노드가 그대로예요.** 이미 문서에 있는 노드를 넘기면 브라우저는 복사하지 않고 원래 자리에서 떼어 새 자리로 옮겨요. 체크 상태, 입력값, 이벤트 핸들러가 모두 따라가요.
- **이동은 인덱스가 아니라 상대 순서로 판단해야 해요(B 제외).** 인덱스는 추가 · 삭제만으로도 밀려서, 양쪽에 다 있는 노드끼리의 순서가 그대로여도 이동으로 잡혀요.
- **C는 흔한 경우를 최소로 처리하면서 가장 단순해요.** 실제 앱의 목록 변경은 대부분 끝에 추가, 중간 삭제, 한 항목 이동이에요. C가 손해를 보는 경우는 맨 뒤를 맨 앞으로 옮길 때뿐이고, 그때도 화면 결과는 맞아요.
- **D는 이동 횟수만 줄여 줘요.** 화면 결과는 C와 같고, 우리 앱의 목록 규모에서는 차이를 체감하기 어려워요. ADR-002의 판단을 그대로 따라요.

## 예상되는 결과

- 긍정적 영향:
  - 순서가 바뀌어도 항목의 DOM 노드와 그 안의 상태(체크, 입력값, 포커스)가 유지돼요.
  - 맨 앞이나 중간에 끼워도 뒤의 노드가 바뀐 노드로 잡히지 않아요. ADR-002의 Phase 1 한계가 풀려요.
  - 실제 React와 같은 판단 방식이라, 결과를 React와 비교해 설명할 수 있어요.
- 부정적 영향 / 리스크:
  - Diff 결과의 "i번째 칸 = 부모의 i번째 자식" 약속이 깨져요. 칸마다 이전 몇 번 노드인지 알려 줘야 하고, Patch에 새 순서대로 배치하는 단계가 생겨요. `pairChildren`만 바꾸는 것보다 변경 범위가 커요.
  - 맨 뒤 노드를 맨 앞으로 옮기면 이동이 필요보다 많이 잡혀요. 변경 표시에서도 여러 노드가 이동한 것으로 보여요. 발표와 문서에 한계로 적어요.

## 영향받는 요구사항

없음. Phase 2 요구사항에는 아직 key 기반 Diff · Patch 요구사항이 없어요. Diff · Patch 요구사항을 쓸 때 이 결정을 따라요.
