# ADR-013: 두 영역은 Virtual DOM 트리를 toDOM으로 변환한 DOM으로 렌더링하고, HTML 파싱은 Virtual DOM 트리를 만들 때만 쓴다

- 상태: 제안됨
- 관리 범위: mini-react 저장소 (docs/adr)

## 개요

검증 페이지의 두 영역을 무엇으로 그릴지에 대한 결정이에요. 이 글을 읽으면 왜 [ADR-004](ADR-004.md)를 뒤집어 화면을 Virtual DOM 트리에서 그리는지, 로드·Patch·기록 이동 때 각 영역을 어떤 순서로 그리는지 알 수 있어요.

## 맥락

[ADR-004](ADR-004.md)는 두 영역이 처음부터 어긋나지 않도록 테스트 영역을 항상 HTML 코드를 파싱한 DOM으로 그리기로 했어요. [ADR-010](ADR-010.md)은 기록 이동 때 실제 영역도 `innerHTML`로 바꾸기로 했어요. 그래서 지금 `toDOM`은 Patch가 새 노드를 만들 때만 쓰여요.

그런데 과제 문서는 Virtual DOM 트리에서 화면을 그리라고 해요.

- 로드: "방금 만든 Virtual DOM을 이용하여 테스트 영역을 렌더링합니다."
- 뒤로가기, 앞으로가기: "state history에 저장된 특정 Virtual DOM으로 이동 가능하며 실제 영역, 테스트 영역도 함께 변경되어야 합니다."

Phase 2의 렌더링도 컴포넌트가 만든 Virtual DOM 트리를 DOM으로 바꿔 그려요. React와 같은 방식이에요. Phase 1의 검증 페이지는 이 Virtual DOM → DOM 변환을 화면에서 연습하고 확인하는 곳이어야 해요. 지금은 변환을 FR-E02 단위 테스트로만 확인해요.

## 고려한 선택지

### 선택지 A: 지금처럼 HTML 코드를 파싱한 DOM으로 그린다 (ADR-004 유지)

- 장점: 두 영역이 항상 브라우저 파서 결과와 같아요. 고칠 것이 없어요.
- 단점: 과제 문서의 로드, 기록 이동 문장과 맞지 않아요. `toDOM`이 화면에서 쓰이지 않아 Phase 2 렌더링과 이어지지 않아요.

### 선택지 B: 로드 때만 테스트 영역을 `toDOM`으로 그린다

- 장점: 과제 문서의 로드 문장과 맞아요. 고칠 곳이 한 곳이에요.
- 단점: 로드 때는 Virtual DOM 트리, Patch와 기록 이동 때는 HTML 코드로 그려 경로가 다시 둘로 나뉘어요. ADR-004가 풀려던 불일치가 방향만 바뀌어 다시 생겨요.

### 선택지 C: 화면은 모두 `toDOM`으로 그리고, HTML 파싱은 Virtual DOM 트리를 만들 때만 쓴다

- 장점: 로드, Patch, 기록 이동이 모두 "Virtual DOM 트리 → DOM" 한 경로로 그려져요. 과제 문서와 맞고, Phase 2 렌더링과 같은 방식이에요. `toDOM`이 매번 화면에서 쓰여 변환 버그가 드러나요.
- 단점: `toDOM`이 지원하지 않는 입력(SVG 등)은 테스트 영역도 브라우저와 다르게 그려져요. `toDOM`으로 만든 `<script>`는 실행돼요.

## 결정

두 영역의 렌더링 결과는 Virtual DOM 트리를 `toDOM`으로 변환한 DOM으로 만든다. HTML 코드는 Virtual DOM 트리를 만들 때만 파싱하고, 파싱한 DOM을 화면에 붙이지 않는다.

시점별 순서는 다음과 같다.

1. 로드
   1. 실제 영역에 샘플 HTML 코드를 넣어 렌더링한다. 과제 문서에서 샘플 HTML 코드는 실제 영역에 주어진 입력이다.
   2. 실제 영역의 DOM 트리를 `toVNode`로 Virtual DOM 트리로 변환한다.
   3. 그 트리를 `toDOM`으로 변환해 테스트 영역을 렌더링한다.
2. Patch
   1. 입력창의 HTML 코드를 화면 밖 문서(`createHTMLDocument`)의 컨테이너에서 파싱하고, `toVNode`로 새 Virtual DOM 트리를 만든다.
   2. 새 트리를 `toDOM`으로 변환해 테스트 영역을 렌더링한다.
   3. 실제 영역은 지금처럼 Diff 결과로 Patch한다.
3. 기록 이동
   1. 이동한 기록의 `vdom`을 `toDOM`으로 변환해 두 영역을 모두 렌더링한다.
   2. 실제 영역은 Diff와 Patch를 거치지 않고 기록의 상태 전체로 바꾼다. 요구사항 4.3절과 ADR-010의 근거를 그대로 따른다.
4. 확인
   1. 테스트 영역을 `toDOM`으로 렌더링한 뒤, 그 DOM을 다시 `toVNode`로 변환해 원래 트리와 Diff한다. 다르면 오류 메시지를 보여 준다.
   2. Patch 후 두 영역 비교(FR-W15)는 지금처럼 한다. 비교 기준은 1단계에서 파서로 만든 새 트리다.

## 근거

C만 세 시점의 렌더링 경로를 하나로 만들면서 과제 문서와 맞아요. B는 과제의 로드 문장만 맞추고 불일치를 남겨요.

ADR-004가 C 쪽(그때의 선택지 A)을 고르지 않은 이유는 "변환이 불완전하면 변환 버그가 두 영역에 똑같이 생겨 드러나지 않는다"였어요. 이 결정에서는 두 가지로 이 문제를 막아요.

- 비교 기준을 테스트 영역의 DOM이 아니라 브라우저 파서로 만든 Virtual DOM 트리로 둬요. 파서는 엔진을 거치지 않으니 엔진 버그와 상관없는 기준이 돼요.
- 결정 4-1의 왕복 확인으로 `toDOM` 버그를 화면에서 바로 알려요.

입력은 여전히 브라우저가 파싱한 DOM에서 만들어요. 그래서 [ADR-005](ADR-005.md)(입력 보정)와 [ADR-009](ADR-009.md)(파서의 512단계 깊이 상한)의 전제는 그대로예요.

## 예상되는 결과

- 긍정적 영향: 검증 페이지가 "Virtual DOM 트리 → DOM" 렌더링을 화면에서 보여 줘요. Phase 2 렌더링과 같은 흐름이라 발표 때 Phase 1과 Phase 2를 한 흐름으로 설명할 수 있어요.
- 긍정적 영향: `toDOM` 버그가 로드 때 왕복 확인과 기록 이동 때 화면에서 드러나요.
- 부정적 영향 / 리스크: [Virtual DOM 설계](../design/vdom.md)가 SVG·MathML을 지원하지 않아요. 이런 입력은 테스트 영역도 브라우저와 다르게 그려지고, 결정 4-1의 확인에 걸려요. 지원하려면 `ns` 필드와 `createElementNS`가 필요해요.
- 부정적 영향 / 리스크: `toDOM`의 `createElement`로 만든 `<script>`는 문서에 붙을 때 실행돼요. 지금은 실제 영역에서만 실행되지만, 이 결정 뒤에는 테스트 영역에서도 실행돼요. 스크립트 실행 정책은 요구사항 7절의 추후 논의 항목이에요.
- 부정적 영향 / 리스크: [검증 페이지 설계](../design/page.md)의 로드, Patch, 기록 이동, 오류 처리 흐름과 `src/phase1/page/page.ts`를 고쳐야 해요.
