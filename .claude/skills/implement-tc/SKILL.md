# 테스트 케이스 기반 1차 구현

입력: `$ARGUMENTS`

이 스킬이 고치는 파일은 테스트가 아닌 `src/` 코드예요. `src/**/*.test.ts`와 요구사항, 설계, ADR 문서는 읽고 보고만 해요. 설계에 맞춰 구현을 다듬는 일은 다음 단계(2차 구현)에서 해요. 워크플로우는 `.claude/skills/README.md`의 "쓰는 순서" 절을 봐요.

## 0. 입력 확인

- 첫 단어는 Phase예요. `.claude/skills/README.md`의 "Phase 인자" 절에 적힌 대로 읽어요. Phase가 비어 있거나 `docs/requirements/` 아래에 없는 값이면, 그 절대로 고를 수 있는 Phase를 보여 주고 AskUserQuestion으로 물어요. 추측해서 진행하지 않아요.
- 둘째 단어부터는 대상이에요. 테스트 파일 경로(예: `src/diff.test.ts`)나 요구사항 ID(예: `FR-E03`)를 받아요. 요구사항 ID면 테스트 주석에 그 ID가 있는 케이스를 대상으로 해요. 없으면 그 Phase 요구사항 ID가 적힌 테스트 전체를 대상으로 해요.
- 준 경로가 없거나, 그 ID가 적힌 테스트가 없으면 멈추고 알려요. 테스트가 없으면 `/make-testcase`를 먼저 돌리라고 안내해요.

## 1. 테스트 상태 확인

`npm test`로 테스트를 돌려 대상 테스트의 상태를 아래 형식으로 보여 줘요.

| 테스트 파일 | 케이스 | 요구사항 ID | 결과 (통과 / 실패) | 실패 이유 (한 줄) |
| ----------- | ------ | ----------- | ------------------ | ----------------- |

- 대상 테스트가 모두 통과면 구현할 것이 없다고 알리고 끝내요.
- 테스트 코드 자체가 돌지 않으면(문법 오류, 없는 import 경로) 멈추고 알려요. 테스트는 이 스킬이 고치지 않아요.
- 구현을 시작하기 전에 테스트 파일 스냅숏을 적어 둬요. `git ls-files -co --exclude-standard -- '*.test.ts' | xargs git hash-object`로 파일 목록과 내용 해시를 남겨요. 아직 커밋하지 않은 새 테스트 파일과 스테이지된 변경까지 잡기 위해서예요.

## 2. 읽을 문서

구현 전에 아래를 읽어요.

1. 실패한 테스트 파일 전부 — 기대 결과의 기준
2. 테스트할 모듈의 `src/` 코드와 그 모듈이 쓰는 다른 모듈
3. 테스트 주석에 적힌 요구사항 ID의 요구사항 행 — 테스트가 요구사항과 맞는지 볼 때 써요.
4. 이 Phase의 설계 문서가 있으면 "인터페이스" 절 — 함수 이름과 시그니처만 맞춰요. 내부 구조는 따르지 않아도 돼요.
5. 테스트 관례: `.claude/skills/make-testcase/SKILL.md` 4단계 "형식 지키기"

## 3. 계획 확인

실패한 테스트를 묶어 구현 순서를 정해요. 다른 함수가 의존하는 함수부터 해요.

| 순서 | 구현할 곳 (파일, 함수) | 통과시킬 케이스 | 요구사항 ID |
| ---- | ---------------------- | --------------- | ----------- |

표를 보여 주고 확인을 받아요.

## 4. 구현

### 지킬 것

- 테스트 파일은 고치지 않아요. 테스트의 기대 결과가 요구사항과 어긋나 보이면, 그 케이스는 구현하지 않고 멈춰서 AskUserQuestion으로 물어요.
  - **테스트대로 구현** (추천): 테스트를 기준으로 구현하고, 어긋난 곳은 보고에 적어요.
  - **이 케이스 건너뛰기**: 실패로 두고 다음 묶음으로 넘어가요. 테스트를 고치는 일은 사용자나 `/make-testcase`가 해요.
- 테스트를 통과시키는 데 필요한 코드만 써요. 다음 단계에서 쓸 추상화나 옵션을 미리 넣지 않아요.
- 같은 모듈의 기존 코드 관례(파일 위치, export 방식, 주석 언어)를 따라요.

### 순서

3단계 표의 순서대로 묶음마다 아래를 반복해요.

1. 그 묶음의 케이스를 통과하도록 구현해요.
2. `npm test`로 테스트 전체를 다시 돌려요.
3. 이미 통과하던 테스트가 깨졌으면 다음 묶음으로 넘어가지 않고 먼저 고쳐요.

## 5. 검증

1. **테스트**: `npm test`로 전체 테스트를 돌려요. 대상 케이스가 모두 통과하고, 처음에 통과하던 테스트가 그대로 통과해요.
2. **타입 검사**: `npm run typecheck`가 통과해요.
3. **테스트 파일**: 1단계와 같은 명령으로 스냅숏을 다시 떠서, 파일 목록과 내용 해시가 시작할 때와 같은지 확인해요. (`git diff --stat`은 커밋 안 된 새 파일과 스테이지된 변경을 놓쳐요.)
4. **문서 검수**: 이 스킬은 문서를 쓰지 않아요. 보고에 "검수할 문서 없음"이라고 적어요.

검증 결과는 아래 형식으로 보고해요.

| # | 항목 | 결과 | 문제 위치 | 고칠 내용 |
| - | ---- | ---- | --------- | --------- |

- 이번에 고친 구현 코드의 문제는 바로 고치고 다시 검증해요.
- 테스트, 요구사항, 설계 문서를 고쳐야 하는 문제는 고치지 않고 보고만 해요.

## 6. 마지막 보고

- 고친 파일 목록
- 검증 결과 표 (`npm test` 통과·실패 수, 처음과 비교)
- 아직 실패하는 케이스와 이유 (건너뛴 케이스 포함)
- 테스트와 요구사항이 어긋난 곳
- 설계 문서 인터페이스와 다르게 구현한 곳 (2차 구현에서 맞출 것)
