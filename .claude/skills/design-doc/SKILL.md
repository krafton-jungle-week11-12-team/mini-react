# 설계 문서 작성

입력: `$ARGUMENTS`

## 0. 입력 확인

- 첫 단어는 Phase예요. `.claude/skills/README.md`의 "Phase 인자" 절대로 읽어요.
- 둘째 단어부터는 설계할 모듈 이름이에요. 없으면 그 Phase의 요구사항 문서 전체를 대상으로 해요.

## 1. 요구사항 문서 완성 확인

설계를 시작하기 전에 `docs/requirements/<phase>/` 아래 요구사항 문서 **전부**가 완성됐는지 먼저 확인해요. 모듈 이름을 줬어도 Phase 전체를 확인해요. 설계 문서끼리 서로 이어지기 때문이에요.

문서마다 아래를 확인해요.

1. **안내 주석**: 템플릿의 `<!-- ... -->` 주석(작성 규칙, 섹션 안내)이 남아 있지 않아요.
2. **자리표시자**: `[YYYY-MM-DD]`, `[이름]`, `[목표]`, `[항목]`, `[이유]`, `[용어]`, `[뜻]`, `[흐름 이름]`, `[단계]`, `[유형]`, `[요구사항]`, `[확인 방법]`, `FR-X[번호]`처럼 템플릿 그대로인 칸이 없어요.
   - 백틱 안의 코드(`hooks[i]`, `[vnode]` 등)와 링크(`[글자](경로)`)는 자리표시자가 아니에요. 코드를 빼고 찾아요.
3. **필수 섹션**: 1절 목표 ~ 6절 설계로 넘기는 항목이 모두 있고, 각 절에 실제 내용이 있어요. 7절 추후 논의는 비어 있어도 돼요.
4. **기능 요구사항**: 5절 표마다 요구사항이 하나 이상 있고, 모든 행에 ID·유형·요구사항·확인 방법이 채워져 있어요. 비고가 "삭제됨"인 행은 빼고 봐요.
5. **헤더 표**: 작성일, 작성자, 근거가 채워져 있어요.
6. **승인 대기 ADR**: 비고에 `ADR-00X 승인 시 수정`이 붙은 요구사항이 있으면 적어요. 미완성으로 보지는 않지만, 그 요구사항은 설계가 바뀔 수 있다고 알려요.

참고로 "문서 상태" 값(초안, 통합본 등)만으로는 미완성이라고 판단하지 않아요. 결과 보고에만 적어요.

결과는 아래 형식으로 보여 줘요.

| 요구사항 문서 | 문서 상태 | 결과 (완성 / 미완성) | 남은 항목 (줄 번호와 내용) |
| ------------- | --------- | -------------------- | -------------------------- |

- 모두 완성이면 2단계로 넘어가요.
- 하나라도 미완성이면 멈추고 AskUserQuestion으로 물어요. 미완성 문서를 대신 채우지 않아요.
  - **중단** (추천): 요구사항을 먼저 완성하고 다시 실행해요.
  - **완성된 문서만 설계**: 미완성 문서의 모듈은 빼고 진행해요. 5단계 커버리지 검증과 6단계 보고에 "요구사항 미완성으로 제외"라고 적어요.

## 2. 읽을 문서

작성 전에 아래를 모두 읽어요.

1. `docs/requirements/<phase>/` 아래 요구사항 문서 전부
2. `docs/design/TEMPLATE.md` — 설계 문서 형식. 4단계 "템플릿 형식 지키기"대로 이 형식을 그대로 따라요.
3. `docs/technical-writing-principles.md` — 문장 기준 (`.claude/rules/docs-writing.md`가 가리키는 원칙)
4. `docs/adr/` — 상태가 "제안됨", "승인됨"인 ADR 중 이 Phase 요구사항과 관련된 것
5. 이미 있는 설계 문서
   - 설계 문서는 Phase마다 `docs/design/<phase>/` 아래에 있어요. (예: `docs/design/phase1/`)
   - 앞 Phase의 설계 문서도 읽어요. 새 설계가 앞 Phase의 타입과 함수(예: `VNode`, `toDOM`, `diff`)를 이어받기 때문이에요.
6. 앞 Phase 설계와 실제 코드가 다를 수 있으니 `src/`에서 관련 타입과 함수 시그니처를 확인해요.

## 3. 모듈 나누기

- 템플릿 규칙대로 한 문서에 모듈 하나만 다뤄요.
- 요구사항 문서의 기능 요구사항(5절) 그룹과 동작 흐름(4절)을 보고 모듈을 나눠요.
- 쓰기 전에 아래 표를 사용자에게 보여 주고 확인을 받아요. 이미 있는 문서를 고치는 경우도 표에 적어요.

| 설계 문서 경로 | 모듈 | 다루는 요구사항 ID | 새로 작성 / 수정 |
| -------------- | ---- | ------------------ | ---------------- |

## 4. 설계 문서 작성

### 템플릿 형식 지키기

새 문서는 `docs/design/TEMPLATE.md`를 복사해서 시작하고, 형식을 바꾸지 않고 칸만 채워요. 기존 문서를 고칠 때도 같은 형식에 맞춰요.

- **제목**: `# <모듈 이름> 설계` 한 줄이에요.
- **머리 정보**: 제목 바로 아래에 `- 상태:`, `- 작성자:`, `- 관련 이슈:` 세 줄을 이 순서로 둬요.
- **섹션**: 아래 `##` 섹션을 이 이름, 이 순서 그대로 둬요. 이름을 바꾸거나 순서를 바꾸지 않아요.
  1. 개요 2. 다루는 요구사항 3. 위치와 흐름 4. 자료구조 5. 인터페이스 6. 동작 방식 7. 설계 결정 8. 경계 케이스 9. 검증 방법 10. 정하지 않은 것 11. 관련 문서
  - 지울 수 있는 섹션은 "정하지 않은 것" 하나예요. 나머지는 해당 내용이 없어도 지우지 않고 "없음"과 이유를 한 줄로 써요.
  - 템플릿에 없는 `##` 섹션을 새로 만들지 않아요. 더 나눌 내용은 해당 섹션 아래 `###`로 둬요. (예: 동작 방식 아래 함수별 `###`)
- **섹션 안 형식**: 템플릿이 정한 모양을 그대로 써요.
  - 개요: 첫 문장은 "~은 ~을 해요. 이 문서를 읽으면 ~을 할 수 있어요." 꼴이에요.
  - 다루는 요구사항: `ID | 요구사항 요약 | 이 문서에서 다루는 곳` 표예요.
  - 위치와 흐름: `text` 코드 블록의 `[앞 단계] → [이 모듈] → [다음 단계]` 흐름과 "입력을 주는 곳", "출력을 받는 곳" 두 줄이에요.
  - 자료구조: `ts` 코드 블록으로 타입을 쓰고, 그 아래 속성마다 `` - `속성: 타입` — 의미. 허용 형식. (예: 실제 값) `` 줄을 둬요.
  - 인터페이스: 외부에서 부르는 함수만 `ts` 코드 블록으로 쓰고, 함수마다 파라미터, "반환값:", "부수 효과:" 줄을 둬요. 부수 효과가 없으면 "없음"이라고 써요.
  - 동작 방식: 번호 목록으로 단계를 쓰고, `입력:`·`출력:`이 있는 `text` 예시 블록을 하나 이상 둬요.
  - 설계 결정: `결정 | 이유 | 관련 ADR` 표예요. ADR이 없으면 `-`를 써요.
  - 경계 케이스: `경우 | 입력 예시 | 기대 동작 | 관련 요구사항` 표예요.
  - 검증 방법: "단위 테스트:", "검증 페이지:" 두 줄로 나눠 써요.
  - 관련 문서: 요구사항 명세서 링크를 첫 줄에 둬요.
- **주석**: 템플릿의 작성 규칙 주석과 안내 주석은 다 쓴 뒤 모두 지워요.
- **자리표시자**: `[모듈 이름]`, `[속성]`, `[단계]`처럼 템플릿 그대로인 칸을 남기지 않아요. 예외는 아래 "상태·작성자·관련 이슈" 규칙뿐이에요.

### 내용 규칙

- "다루는 요구사항" 표의 ID와 요약은 요구사항 문서에서 그대로 가져와요. 없는 ID를 만들지 않아요.
- 요구사항 6절 "설계로 넘기는 항목"은 해당 모듈의 "설계 결정" 표에서 정하거나, "정하지 않은 것"에 이유와 함께 남겨요.
- 선택지를 비교해야 할 만큼 큰 결정은 설계 문서에 직접 쓰지 않아요. 사용자에게 ADR이 필요하다고 알리고, "설계 결정" 표에는 `ADR 필요`라고 적어요.
- 설계가 요구사항과 충돌하면 요구사항 본문을 고치지 않아요. `.claude/rules/docs-writing.md`의 ADR 절차를 따르도록 사용자에게 알려요.
- 설계하면서 요구사항에서 부족한 부분을 찾으면 쓰는 동안에는 요구사항을 고치지 않고 "요구사항 반영 목록"에 모아요. 7단계에서 사용자에게 물어 반영해요. 모을 것은 아래와 같아요.
  - **정한 미정 항목**: 요구사항 6.2(미정)나 "설계에서 정한다"고 적힌 항목을 설계에서 정했어요. → 6.1(결정된 항목)로 옮길 내용
  - **새 동작**: 설계에서 정한 동작 중 확인할 수 있는데 요구사항 행이 없는 것이에요. (예: 오류가 나도 상태를 되돌림, boolean attribute 처리) → 새 FR 행
  - **틀린 확인 방법**: 요구사항의 확인 방법대로 해도 기대 결과가 나오지 않는 경우예요. → 확인 방법 수정
  - **흐름 차이**: 요구사항 4절 동작 흐름과 설계 순서가 다른 곳이에요. → 4절 수정
  - **새로 생긴 타입·용어**: 다른 문서가 알아야 하는 타입·용어가 설계에서 생겼어요. → 3절이나 6.1 수정
  - 설계 문서의 "다루는 요구사항"에는 아직 없는 ID를 넣지 않아요. 7단계에서 ID가 생긴 뒤 넣어요.
- 링크는 문서 위치 기준 상대 경로로 써요. (예: `docs/design/phase2/hooks.md`에서 요구사항은 `../../requirements/phase2/...`)
- 상태는 "작성 중", 작성자와 관련 이슈는 모르면 `[이름]`, `#[번호]`로 남기고 마지막 보고에서 알려요.

## 5. 전체 연결성 검증

문서를 다 쓴 뒤 이 Phase의 설계 문서 전체(새 문서 + 기존 문서 + 이어받는 앞 Phase 문서)를 대상으로 아래를 확인해요.

1. **요구사항 커버리지**: 이 Phase 요구사항 문서의 모든 요구사항 ID가 설계 문서 하나 이상의 "다루는 요구사항" 표에 있어요. 범위 제외나 2차 기능이라 일부러 뺀 ID는 이유를 적어요.
2. **없는 ID 참조**: 설계 문서에 적힌 요구사항 ID가 실제 요구사항 문서에 있어요. 요약이 원문과 뜻이 같아요.
3. **설계로 넘기는 항목**: 요구사항 6절 항목마다 어느 문서의 "설계 결정" 또는 "정하지 않은 것"에서 다루는지 짝이 있어요.
4. **입출력 연결**: 각 문서 "위치와 흐름"의 입력을 주는 곳·출력을 받는 곳이 상대 문서에도 반대 방향으로 적혀 있어요. 한쪽에만 있으면 끊긴 연결이에요.
5. **타입·인터페이스 일치**: 한 문서가 넘기는 값의 타입과 받는 문서의 파라미터 타입이 같아요. 같은 타입 이름을 문서마다 다르게 정의하지 않아요. 앞 Phase 타입을 바꿨다면 바뀐 점과 영향받는 앞 Phase 문서를 적었어요.
6. **동작 흐름 따라가기**: 요구사항 4절의 흐름을 처음부터 끝까지 설계 문서의 인터페이스만으로 따라갈 수 있어요. 중간에 담당 모듈이 없는 단계가 있으면 빠진 설계예요.
7. **ADR 참조**: 링크한 ADR 파일이 있고, 기각된 ADR을 근거로 쓰지 않았어요.
8. **링크**: 문서 안의 상대 링크가 실제 파일을 가리켜요. (`ls`로 확인)
9. **템플릿 형식**: 이번에 쓰거나 고친 문서가 4단계 "템플릿 형식 지키기"를 따라요. 제목, 머리 정보 세 줄, `##` 섹션 이름과 순서, 섹션 안 표의 열 이름, 남은 주석(`<!--`)과 자리표시자를 `grep`으로 확인해요. 기존 문서의 형식 차이는 고치지 않고 보고만 해요.

검증 결과는 아래 형식으로 보고해요.

| # | 항목 | 결과 | 문제 위치 | 고칠 내용 |
| - | ---- | ---- | --------- | --------- |

- 이번에 쓴 문서 안의 문제는 바로 고치고 다시 검증해요.
- 기존 문서, 앞 Phase 문서를 고쳐야 하는 문제는 고치지 않고 보고만 해요.
- 요구사항 문서를 고쳐야 하는 문제는 "요구사항 반영 목록"에 더하고 7단계에서 다뤄요.

## 7. 요구사항 반영

6단계 보고를 마친 뒤, 요구사항 반영 목록이 비어 있지 않으면 AskUserQuestion으로 "요구사항 수정할까요?"라고 물어요. 질문에 반영할 항목 수와 대상 문서를 함께 적어요. 목록이 비어 있으면 묻지 않고 끝내요.

- **수정** (추천): 목록 전부를 요구사항에 반영해요.
- **일부만 수정**: 반영할 항목 번호를 받아 그 항목만 반영해요.
- **수정하지 않음**: 요구사항은 그대로 두고, 목록을 설계 문서의 "정하지 않은 것"에 남겨요.

반영할 때는 아래를 지켜요.

1. 요구사항 문서 형식(EARS 문장, 요구사항 하나에 동작 하나)을 따르고 문장은 "~한다"로 써요.
2. 새 FR 행은 그 표의 마지막 번호 다음 번호를 쓰고, 비고에 `설계 반영`과 근거 설계 문서 링크를 적어요. 지운 번호는 다시 쓰지 않아요.
3. 정한 미정 항목은 6.2에서 6.1로 옮기고 근거를 함께 적어요. 6.2가 비면 "없음"이라고 적어요.
4. 6절을 가리키던 비고(예: `미정 (6절)`)와 4절 흐름도 함께 고쳐요.
