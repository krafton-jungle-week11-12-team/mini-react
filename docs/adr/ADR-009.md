# ADR-009: 트리 순회는 재귀로 한다

- 상태: 승인됨
- 관리 범위: mini-react 저장소 (docs/adr)

## 개요

DOM → Virtual DOM 변환, Virtual DOM → DOM 변환, Diff, Patch에서 트리를 어떻게 순회할지 다시 정한 결정이에요. 이 글을 읽으면 [ADR-003](ADR-003.md)(반복문과 명시적 스택)을 왜 재귀로 바꾸는지, 재귀로 바꿔도 괜찮은 이유와 남는 리스크를 알 수 있어요.

이 ADR이 승인되어 ADR-003은 기각됐어요.

## 맥락

[ADR-003](ADR-003.md)은 변환, Diff, Patch를 모두 반복문과 명시적 스택으로 순회하기로 제안했어요. 근거는 두 가지였어요.

- 사용자가 깊게 중첩한 HTML을 넣으면 재귀는 콜 스택이 넘친다(Stack Overflow).
- 반복문 구조가 Fiber의 작업 루프와 같아, Phase 2에서 작업을 나눠 처리해야 할 때 옮겨 가기 쉽다.

이 방식으로 [Diff 설계](../design/diff.md)와 [Patch 설계](../design/patch.md)를 쓰고 변환을 구현(`src/vdom.ts`)하면서 비용이 드러났어요.

- 변환과 Patch는 부모를 먼저 처리하고 자식으로 내려가기만 해서, 스택으로 바꿔도 코드가 조금 길어지는 정도예요.
- Diff는 자식의 비교 결과를 보고 부모가 `UPDATE`인지 `null`인지 정해요. 스택으로는 이 아래에서 위로의 판단을 할 수 없어서, 같은 요소를 먼저 임시 `UPDATE`로 만들고 스택이 빈 뒤 다시 정리하는 단계가 더 필요해요.

2026-11-10 재논의에서 ADR-003의 두 근거를 다시 따져 봤어요.

- 콜 스택이 넘칠 만큼 트리가 깊어질 수 있는가
- Phase 2(Component, State, Hooks)에 스택이나 Fiber가 필요한가

## 고려한 선택지

### 선택지 A: 반복문과 명시적 스택 유지 (ADR-003)

- 장점: 입력 깊이와 상관없이 콜 스택이 넘치지 않아요. 진행 상태가 배열이라 밖에 저장해 두면 작업을 멈췄다 이어서 할 수 있어요.
- 단점: 재귀보다 코드가 길고 처음 읽을 때 이해하기 어려워요. Diff처럼 자식 결과로 부모를 정하는 작업에는 정리 단계가 더 필요해요. 앞으로 아래에서 위로 판단하는 작업이 생길 때마다 같은 비용이 다시 생겨요.

### 선택지 B: 재귀

함수가 노드 하나를 처리하고, 자식마다 자기 자신을 다시 불러요.

- 장점: 코드가 트리 모양과 닮아 가장 짧고 이해하기 쉬워요. 함수가 돌아올 때 자식 결과를 받아 부모를 정하므로, 아래에서 위로의 판단에 정리 단계가 필요 없어요.
- 단점: 트리가 콜 스택 한도보다 깊으면 넘쳐요. 작업을 중간에 멈출 수 없어요.

### 선택지 C: Fiber

- 장점: 작업을 멈췄다 이어서 할 수 있고, 콜 스택도 넘치지 않아요.
- 단점: Virtual DOM 노드를 Fiber 노드로 바꾸는 단계와 포인터 관리가 더해져 구현량이 가장 많아요. ADR-003에서 이미 이번 과제에 맞지 않는다고 봤어요.

## 결정

변환, Diff, Patch 모두 선택지 B(재귀)로 순회한다. ADR-003을 대체한다.

1. 순서는 깊이 우선으로 한다. 부모를 먼저 처리하고 자식을 앞에서부터 차례로 처리한다.
2. 변환은 노드를 만들고 자식마다 재귀로 만든 결과를 붙인다.
3. Diff는 자식 목록의 비교 결과를 재귀로 받아, 속성이나 자식 중 하나라도 바뀌었으면 `UPDATE`, 아니면 `null`을 돌려준다.
4. Patch는 칸 하나를 적용하고, `UPDATE`면 그 요소와 `children`으로 재귀 호출한다.
5. 재귀 함수 안에서 자식은 `for` 반복문으로 순회한다. `map`, `Array.from` 같은 콜백으로 순회하지 않는다. 콜백이 한 단계마다 호출을 더 쌓아 버틸 수 있는 깊이가 약 4분의 1로 줄어든다.
6. Fiber는 이번 과제에서 쓰지 않는다.

## 근거

- **콜 스택이 넘칠 만큼 깊어지지 않아요.**
  - 샘플 HTML 코드의 깊이는 4~5단계예요.
  - 테스트 영역과 실제 영역은 브라우저가 HTML 코드를 파싱한 DOM으로 만들어요([ADR-004](ADR-004.md), [ADR-005](ADR-005.md)). Chromium 계열 브라우저의 HTML 파서는 요소 중첩을 512단계에서 끊고, 더 깊은 요소는 형제로 붙여요. 사용자가 `<div>`를 수만 번 중첩해 넣어도 DOM은 512단계를 넘지 않아요.
  - 2026-11-10 Chrome 156에서 확인했어요. `innerHTML`로 511·512단계를 넣으면 그대로 511·512단계이고, 513·1,000·5,000단계를 넣으면 모두 512단계로 잘려요. `DOMParser`로 문서 전체를 파싱해도 같은 상한이 걸려요.
  - 실제 구현(`src/vdom.ts`, `src/diff.ts`)이 버티는 요소 중첩 깊이를 같은 Chrome 156에서 재 봤어요. 파서 상한을 피하려고 `createElement`로 `<div>`를 일자로 깊게 쌓아 쟀어요. 형제 수는 `for` 반복문으로 돌아서 한도에 영향을 주지 않아요.

    | 함수 | 최대 깊이 |
    | --- | --- |
    | `toVNode` | 7,501 |
    | `toDOM` | 3,281 |
    | `diff` | 2,812 |

    Patch 흐름(`toVNode` → `diff` → `patch`)은 이 함수들을 차례로 부르므로, 전체 한도는 가장 낮은 `diff`(약 2,800단계)에 묶여요. 그래도 512단계보다 약 5.5배 여유가 있어요. 한도 근처에서는 브라우저가 코드를 최적화하는 시점에 따라 값이 수백 단계씩 흔들려요. Node 26에서 잰 값(2,500~3,750)과도 비슷해요.
  - 결정 5번의 근거: 재귀 Diff 프로토타입을 Node 26에서 재 보니 자식을 `for` 반복문으로 돌면 6,250단계, `Array.from` 콜백으로 돌면 1,562단계까지 버텼어요.
- **Phase 2도 재귀로 구현할 수 있어요.** React 15는 재귀로 컴포넌트와 State를 지원했어요. Hooks는 지금 렌더링 중인 컴포넌트와 훅 호출 순서만 알면 되고, 순회 방식과는 상관없어요. 게다가 과제 제약상 Hook과 State는 루트 컴포넌트에만 있고, 자식 컴포넌트는 props만 받는 순수 함수예요. 그래서 자식 컴포넌트는 렌더링 때 함수 호출로 바로 펼쳐져 VNode 트리 하나가 되고, 컴포넌트 인스턴스 트리나 자식부터 실행할 effect가 없어요. 재귀로 짠 프로토타입(`h`, `toDOM`·`diff`·`patch`, `FunctionComponent`, `useState`·`useEffect`·`useMemo`)으로 상태 변경 → Diff → Patch가 바뀐 노드만 고치는 것을 확인했어요.
- **Fiber로 갈 일이 없어요.** Fiber가 필요한 이유는 큰 화면을 그리다 멈추고 사용자 입력을 먼저 처리하는 것이에요. Phase 2 범위(Component, State, Hooks)에 작업 중단은 없고, 화면도 작아요. 그래서 ADR-003의 두 번째 근거(Fiber로 옮겨 가기 쉽다)도 이번 과제에서는 쓸 일이 없어요.
- **재귀가 더 이해하기 쉬워요.** 코드가 트리 모양과 닮아서 설계 문서, 코드 리뷰, 발표에서 설명하기 쉬워요. Diff의 임시 `UPDATE`와 정리 단계처럼 스택 때문에 생긴 장치가 사라져요.

## 예상되는 결과

- 긍정적 영향:
  - Diff 설계에서 임시 `UPDATE`, 확인할 `UPDATE` 목록, 정리 단계가 사라지고 코드가 짧아져요.
  - Phase 2에서 Diff에 판단 규칙을 더할 때(예: 이벤트 핸들러 비교) 함수가 돌아오는 자리에 바로 넣으면 돼요.
  - 일정이 빠듯한 Diff·Patch 구현(#14)을 더 빨리 끝낼 수 있어요.
- 부정적 영향 / 리스크:
  - 파서를 거치지 않고 Virtual DOM 트리를 직접 만드는 경로(단위 테스트, Phase 2 컴포넌트)에는 깊이 제한이 없어요. 이 경로에서 1,500단계 이상 깊은 트리를 만들면 콜 스택이 넘칠 수 있어요(`for` 반복문으로 짜면 6,000단계 이상). Phase 2 컴포넌트는 사람이 직접 쓰는 코드라 이렇게 깊어지지 않아요.
  - 512단계 제한과 재귀 한도는 Chrome 156에서 확인한 값이에요. Firefox와 Safari는 파서 상한과 스택 크기를 확인하지 않았어요. 발표와 검증은 Chromium 계열 브라우저에서 해요.
  - 깊이는 단위 테스트하지 않아요. 실제 입력은 파서 때문에 512단계를 넘을 수 없고 재귀 한도까지 5배 이상 여유가 있어서, 위 측정으로 대신해요. 테스트 환경인 jsdom에는 파서 깊이 제한이 없어서 이 상한을 테스트로 확인할 수도 없어요.
  - 이미 스택으로 쓴 문서와 코드를 다시 고쳐야 해요.
    - `src/vdom.ts`의 `toVNode`, `toDOM`과 테스트
    - [Virtual DOM 변환 설계](../design/vdom.md)의 동작 방식과 설계 결정
    - [Diff 설계](../design/diff.md)의 동작 방식, 설계 결정, 검증 방법(`UPDATE` 정리 단위 테스트)
    - [Patch 설계](../design/patch.md)의 동작 방식, 설계 결정
  - 작업 중단이 필요해지면 재귀로는 할 수 없어요. 그때는 Fiber를 새 ADR로 검토해요.
