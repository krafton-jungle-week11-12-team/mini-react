# ADR-001: 구현 언어로 TypeScript를 쓴다

- 상태: 승인됨
- 관리 범위: mini-react 저장소 (docs/adr)

## 개요

React의 핵심 동작을 직접 구현하는 과제에서 어떤 언어로 구현할지에 대한 결정이에요. 이 글을 읽으면 C/Python(WebAssembly)과 JavaScript를 두고 왜 TypeScript를 골랐는지, 그리고 TypeScript의 부담을 어떻게 줄이기로 했는지 알 수 있어요.

## 맥락

이번 과제는 Diff 알고리즘으로 브라우저 DOM을 갱신하는 부분부터 Phase 2의 Hooks까지 직접 구현해야 해요. 첫 번째 회의에서 첫 ADR 주제를 "구현 언어 선택 (JavaScript vs TypeScript)"으로 정했어요.

언어를 조사하던 중 Diff 알고리즘을 보기 쉽게 C 코드로 받아 보려 했는데, C와 Python에는 DOM 자료구조가 없어 새로 정의해야 한다는 답을 받았어요. 그래서 JavaScript 계열이 아닌 언어(C/Python + WebAssembly)도 선택지에 넣어 함께 검토했어요.

또 구현의 많은 부분을 AI의 도움을 받아 진행할 예정이어서, 사람이 AI가 만든 코드를 얼마나 쉽게 검증할 수 있는지도 중요한 기준이었어요.

## 고려한 선택지

검토한 대안과 장단점은 다음과 같아요.

### 선택지 A: C / Python (WebAssembly)

- 장점: C는 계산 속도가 빨라요. 이미지 처리처럼 계산이 무거운 작업에는 WebAssembly가 잘 맞아요.
- 단점: 브라우저(C++ 렌더링 엔진)는 DOM을 JavaScript에서 쓰기 쉽게 열어 두었기 때문에, C/Python에서 DOM을 다루려면 자료구조를 새로 정의하고 변환해야 해요. WebAssembly 환경에서 실행하더라도 DOM API를 호출하려면 다시 JavaScript를 거쳐야 해서, Diff → 변환 → DOM 반영 → 다시 가져와 변환하는 과정이 반복돼요. 이때 드는 직렬화·역직렬화 비용이 계산 속도로 얻는 이득과 비슷해요.

### 선택지 B: JavaScript

- 장점: 브라우저가 DOM을 JavaScript에 열어 두었기 때문에 DOM 작업과 바로 맞물려요. Phase 2에서 Hooks를 구현할 때 필요한 JavaScript 함수의 특성(클로저 등, Phase 2 학습 후 구체화)을 그대로 쓸 수 있어요. 별도 설정이나 새 문법 학습이 필요 없어요.
- 단점: 타입이 맞지 않는 문제를 실행해 봐야 알 수 있어요. 함수나 자료구조에 무엇이 와야 하는지 코드만으로 드러나지 않아, AI가 잘못된 값을 넣어도 바로 알아채기 어려워요.

### 선택지 C: TypeScript

- 장점: JavaScript로 컴파일되기 때문에 JavaScript의 장점(DOM 작업, 함수 특성)을 그대로 가져가요. 타입 에러를 실행 전(컴파일 단계)에 잡을 수 있어요. 타입 설계 자체가 "여기엔 무엇이 와야 한다"는 명세가 되어 문서 역할을 해요. 타입이 AI 코드의 검증 도구가 돼요. 예를 들어 `children`에 `VNode`가 와야 하는데 AI가 실수로 다른 값을 넣으면 바로 에러가 나요. 요즘 대부분 TypeScript를 써서 이력서에 넣기에도 좋아요.
- 단점: 설정과 타입 등 신경 쓸 것이 늘고, 문법을 새로 공부해야 할 수 있어요.

## 결정

구현 언어는 TypeScript로 한다. 타입(자료형) 설계는 사람이 직접 하고, 구현은 AI에게 맡긴다. 사람은 AI가 짠 코드를 읽을 수 있는 수준까지 TypeScript를 익힌다.

## 근거

이번 과제의 중심은 무거운 계산이 아니라 DOM 조작이에요. C/Python은 계산이 빠르지만 DOM을 오가며 변환하는 비용이 그 이득을 상쇄하기 때문에, DOM과 바로 맞물리는 JavaScript 계열이 맞다고 판단했어요. Phase 2의 Hooks도 JavaScript 함수의 특성을 활용해야 해요.

JavaScript 계열 중에서는 TypeScript를 골랐어요. TypeScript는 JavaScript로 컴파일되므로 위 장점을 그대로 유지하면서, 타입 에러를 실행 전에 잡고 타입을 명세로 쓸 수 있어요. 특히 구현을 AI에게 맡기는 상황에서는 타입이 AI 코드를 검증하는 기준이 돼요. 설정과 학습 부담은 사람이 타입 설계까지만 맡고 구현은 AI에게 맡기는 방식으로 줄일 수 있다고 봤어요. 이력서에 쓰기 좋다는 점도 함께 고려했어요.

## 예상되는 결과

이 결정으로 예상되는 영향은 다음과 같아요.

- 긍정적 영향: 타입이 명세 역할을 해서 팀원끼리, 그리고 사람과 AI 사이에 "무엇이 와야 하는지"가 분명해져요. AI가 만든 코드의 타입 오류를 실행 전에 잡을 수 있어요.
- 부정적 영향 / 리스크: 빌드 도구와 tsconfig(strict 여부 등) 초기 설정이 필요한데, 아직 정하지 않았어요(추후 결정). 사람이 코드를 읽을 수 있는 수준까지만 익히면 타입으로 잡히지 않는 로직 오류를 놓칠 수 있어요. 타입 설계가 늦어지면 AI 구현도 함께 늦어져요.
