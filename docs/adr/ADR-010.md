# ADR-010: 기록 이동 때 실제 영역은 기록의 HTML 코드를 파싱한 DOM으로 바꾼다

- 상태: 승인됨
- 관리 범위: mini-react 저장소 (docs/adr)

## 개요

뒤로가기, 앞으로가기 때 실제 영역을 어떻게 되돌릴지에 대한 결정이에요. 이 글을 읽으면 왜 기록 이동에는 Diff와 Patch를 쓰지 않고, 기록의 `html`을 `innerHTML`로 넣어 실제 영역을 바꾸는지 알 수 있어요.

## 맥락

요구사항 4.3은 기록을 이동할 때 "바뀐 노드만 고치는 것이 아니라 기록의 상태 전체로 바꾼다"고 정했어요. 다만 실제 영역을 어떤 방법으로 바꿀지는 설계로 넘겼어요(요구사항 6절). 어느 방법이든, 이동한 뒤 실제 영역의 DOM은 이동한 기록의 `vdom`과 같은 구조여야 해요. 다음 Patch가 현재 위치 기록의 `vdom`을 이전 트리로 쓰기 때문이에요.

## 고려한 선택지

### 선택지 A: 기록의 `html`을 `innerHTML`로 넣는다

- 장점: 테스트 영역과 같은 방법이라 구현이 단순해요. 같은 HTML 코드를 같은 파서로 파싱하므로 실제 영역이 이동한 기록의 `vdom`과 같은 구조가 돼요.
- 단점: 실제 영역의 노드가 모두 새 객체로 바뀌어요. 이동할 때는 바뀐 부분을 강조 표시할 수 없어요.

### 선택지 B: 현재 위치 기록과 이동할 기록의 `vdom`을 Diff하고 Patch한다

- 장점: 바뀐 노드만 고쳐요. 이동할 때도 강조 표시할 수 있어요.
- 단점: Diff나 Patch에 버그가 있으면 실제 영역이 기록과 어긋난 채로 남아요. 요구사항 4.3의 "기록의 상태 전체로 바꾼다"와 맞지 않아요.

## 결정

기록 이동 때 실제 영역은 이동한 기록의 `html`을 `innerHTML`로 넣어 바꾼다. Diff와 Patch는 쓰지 않는다.

## 근거

요구사항 4.3이 이미 "기록의 상태 전체로 바꾼다"고 정했어요. A는 그 문장을 그대로 구현해요. 또 A는 Diff와 Patch를 거치지 않아서, 엔진에 버그가 있어도 이동한 뒤의 실제 영역은 항상 기록과 같아요. 엔진 검증은 Patch 버튼 흐름에서 하면 돼요.

## 예상되는 결과

- 긍정적 영향: 기록 이동 뒤 실제 영역이 항상 이동한 기록의 `vdom`과 같은 구조가 돼, 다음 Patch가 맞게 동작해요.
- 부정적 영향 / 리스크: 기록 이동은 바뀐 노드만 고치는 흐름이 아니라서, 이동할 때의 변경은 화면에서 강조 표시되지 않아요.
