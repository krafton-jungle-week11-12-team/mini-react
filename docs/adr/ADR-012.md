# ADR-012: 개념 학습은 Claude로, 문서 작성 · 설계 · 구현은 Claude Code로 한다

- 상태: 제안됨
- 관리 범위: mini-react 저장소 (docs/adr)

## 개요

mini-react 작업에서 Claude(웹 · 데스크톱 앱)와 Claude Code(CLI)를 언제 쓸지에 대한 결정이에요. 이 글을 읽으면 두 도구를 직접 써 보며 겪은 차이와, 작업 단계별로 어떤 도구를 쓰면 되는지 알 수 있어요.

## 맥락

팀은 개념 학습, 문서 작성, 설계, 구현에 Claude와 Claude Code를 섞어 쓰고 있어요. 두 도구 모두 같은 모델을 쓰지만, 화면 구성과 작업 방식이 달라서 단계마다 편한 도구가 달랐어요. 기준이 없으면 사람마다 다른 도구로 같은 일을 하게 되고, 작업 기록과 저장소 상태를 맞추기 어려워요.

직접 써 보며 겪은 차이는 다음과 같아요.

| 항목 | Claude | Claude Code |
| --- | --- | --- |
| 화면 | GUI예요. 시각화, 아티팩트로 개념을 보며 익히기 좋아요. | CLI예요. 명령어를 입력하는 방식이라 프로젝트, 아티팩트 같은 기능을 GUI만큼 자유롭게 쓰기 어려워요. |
| 단계 진행 | 한 번에 끝까지 진행하는 경향이 있어서, 문서 · 설계 · 구현 단계를 나눠 추적하기 어려워요. | 저장소 안에서 단계별로 파일을 만들고 커밋해서, 각 단계를 추적하기 쉬워요. |
| 저장소 동기화 | 프로젝트에 GitHub 저장소를 연결할 수 있지만, 협업 중 무엇이 머지됐는지 몰라서 매번 채팅으로 동기화를 요청하거나 직접 동기화해야 해요. | 자동 동기화는 아니지만 `git pull` 같은 평소 git 명령을 그대로 써요. 익숙한 습관이 그대로 적용돼요. |
| 명령 실행 | 코드를 실행하려면 결과를 복사해 와야 해요. | 테스트, 빌드 같은 명령을 바로 실행하고 결과를 함께 봐서 더 직관적이에요. |
| 프로젝트 이해 · 커스터마이징 | 무엇을 고쳐야 동작이 바뀌는지 GUI에서 찾기 어려워요. | 프로젝트 전체를 읽고 스스로 작업해요. 빠진 규칙은 `CLAUDE.md`, `.claude/rules`, `.claude/skills`에 파일로 넣어서 고칠 수 있어요. |
| 파일 확인 | 저장소 폴더 구조를 보려면 GitHub이나 다른 창을 열어야 해요. | 같은 터미널에서 `ls`, `tree` 같은 명령으로 바로 확인해요. |
| 파일 · 폴더 참조 | 참고할 파일을 직접 올리거나 프로젝트 지식에 넣어야 해요. | 입력창에 `@docs/adr/`, `@docs/adr/TEMPLATE.md`처럼 `@`를 붙여 참고할 폴더와 파일을 바로 지정해요. 경로는 자동 완성돼요. |
| 서브 에이전트 | 사용자가 직접 정의해서 부르는 서브 에이전트 기능은 없어요. | 서브 에이전트를 쓸 수 있어요. 팀은 아직 써 보지 않았어요. |

## 고려한 선택지

### 선택지 A: 모든 작업을 Claude로 한다

- 장점: GUI라 처음 쓰는 사람도 쉽게 써요. 시각화와 아티팩트로 개념을 익히기 좋아요.
- 단점: 한 번에 끝까지 진행해서 단계별로 추적하기 어려워요. 머지된 내용을 매번 동기화해야 하고, 명령을 실행하거나 파일을 확인하려면 다른 창을 오가야 해요.

### 선택지 B: 모든 작업을 Claude Code로 한다

- 장점: 저장소, git, 명령 실행이 한곳에 있어요. `.claude`에 규칙을 넣어 팀 방식대로 맞출 수 있어요.
- 단점: 개념을 그림이나 인터랙티브 예제로 보며 익히기에는 GUI보다 불편해요.

### 선택지 C: 작업 단계에 따라 나눠 쓴다

- 장점: 개념 학습은 Claude의 시각화를, 문서 · 설계 · 구현은 Claude Code의 저장소 연동을 쓸 수 있어요.
- 단점: 두 도구를 오가야 해요. Claude에서 익힌 내용은 저장소에 자동으로 남지 않아서 필요하면 직접 옮겨야 해요.

## 결정

선택지 C를 따른다. 개념 학습은 Claude로, 저장소에 남는 작업(문서 작성, 설계, 구현)은 Claude Code로 한다.

1. 개념을 처음 익히거나 그림 · 아티팩트로 확인하고 싶을 때는 Claude를 쓴다.
2. ADR, 요구사항, 설계 문서, 코드처럼 저장소에 커밋하는 작업은 Claude Code로 한다.
3. Claude에서 정리한 내용 중 팀이 알아야 하는 것은 Claude Code로 저장소 문서나 Discussions에 옮긴다.
4. 반복해서 설명하게 되는 규칙은 채팅에 매번 쓰지 않고 `.claude/rules`나 `.claude/skills`에 넣는다.

## 근거

- **저장소에 남는 작업은 단계별로 추적할 수 있어야 해요.** Claude Code는 단계마다 파일을 만들고 커밋해서, 문서 → 설계 → 구현 순서를 PR 단위로 나눠 볼 수 있어요. Claude는 한 번에 진행해서 이 흐름이 잘 남지 않아요.
- **협업에서는 최신 main을 기준으로 일해야 해요.** Claude Code는 평소 git 명령으로 머지된 내용을 가져와요. Claude는 머지가 있을 때마다 따로 동기화해야 해서 놓치기 쉬워요.
- **팀 규칙을 파일로 관리할 수 있어요.** 문서 작성 규칙(`.claude/rules/docs-writing.md`)이나 설계 문서 스킬처럼, 빠진 부분을 파일로 넣으면 다음 작업부터 자동으로 따라요. 규칙이 PR로 리뷰되고 팀 전체에 적용돼요.
- **명령 실행과 파일 확인이 같은 곳에서 끝나요.** 테스트 결과나 폴더 구조를 터미널에서 바로 봐요. Claude Code 입력창에서 `!`를 앞에 붙이면(예: `! ls docs/adr`) 세션을 끝내지 않고도 셸 명령을 실행할 수 있어요. 실행 결과는 대화에 남아서 Claude Code도 함께 봐요.
- **참고할 범위를 직접 정할 수 있어요.** `@docs/adr/TEMPLATE.md`처럼 `@`로 파일이나 폴더를 지정하면, 파일을 올리지 않아도 그 내용을 기준으로 작업해요. ADR을 쓸 때 템플릿과 기존 ADR을 이렇게 지정했어요.
- **개념 학습에는 Claude의 GUI가 Claude Code보다 나아요.** Diff, Patch 같은 개념은 그림과 인터랙티브 예제로 볼 때 이해가 빨라요. 이 단계는 저장소에 남길 필요가 없어서 Claude Code의 장점이 크지 않아요.

## 예상되는 결과

- 긍정적 영향:
  - 문서 · 설계 · 구현이 저장소와 PR에 단계별로 남아서, 누가 무엇을 언제 바꿨는지 추적할 수 있어요.
  - 팀 규칙이 `.claude`에 쌓여서, 같은 설명을 반복하지 않아도 결과물 형식이 맞춰져요.
  - 개념 학습은 시각화의 도움을 그대로 받아요.
- 부정적 영향 / 리스크:
  - 두 도구를 오가야 해요. Claude에서 익힌 내용을 옮기지 않으면 팀에 공유되지 않아요.
  - CLI에 익숙하지 않은 팀원은 Claude Code에 적응하는 시간이 필요해요.
  - 서브 에이전트는 아직 써 보지 않아서, 이 결정에는 서브 에이전트 활용 방식이 들어 있지 않아요. 써 본 뒤 필요하면 새 ADR로 정해요.

## 최종 정리

| 구분 | Claude | Claude Code |
| --- | --- | --- |
| 한 줄 요약 | 보면서 배우는 도구 | 저장소 안에서 일하는 도구 |
| 잘하는 일 | 개념 설명, 시각화, 아티팩트로 그림과 예제 보기 | 문서 작성, 설계, 구현, 테스트 실행, 커밋과 PR |
| 강점 | GUI라 쉽게 시작해요. 결과를 눈으로 바로 봐요. | 단계별로 추적돼요. git 습관이 그대로 적용돼요. `@`로 참조 범위를 정하고, `!`로 셸 명령을 실행하고, `.claude`로 팀 규칙을 넣어요. |
| 약점 | 한 번에 진행해서 단계를 추적하기 어려워요. 머지된 내용을 매번 동기화해야 해요. 동작을 바꾸려면 어디를 고칠지 찾기 어려워요. | 그림과 인터랙티브 예제로 개념을 익히기에는 GUI보다 불편해요. CLI에 익숙해지는 시간이 필요해요. |
| 이 프로젝트에서 쓰는 때 | 새 개념(Virtual DOM, Diff, key 등)을 처음 익힐 때 | ADR, 요구사항, 설계 문서, 코드를 만들거나 고칠 때 |
