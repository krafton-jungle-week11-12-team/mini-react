# ADR-003: 트리 순회는 반복문과 명시적 스택으로 한다

- 상태: 제안됨
- 관리 범위: mini-react 저장소 (docs/adr)

## 개요

DOM → Virtual DOM 변환, Virtual DOM → DOM 변환, Diff, Patch에서 트리를 어떻게 순회할지에 대한 결정이에요. 이 글을 읽으면 재귀, 반복문과 스택, Fiber 중 무엇을 골랐고 왜 골랐는지, 그리고 이 방식으로 짤 때 지켜야 할 순서를 알 수 있어요.

## 맥락

Phase 1의 핵심 기능은 모두 트리를 처음부터 끝까지 훑어야 해요. 부모를 먼저 처리하고 자식으로 내려가는 깊이 우선(전위) 순서가 자연스러워요. 남은 문제는 이 순서를 **어떻게 구현하느냐**예요.

- React 15는 재귀로 구현했어요.
- React 16부터는 Fiber(자식, 형제, 부모를 가리키는 연결 리스트)와 반복문으로 바꿨어요. 큰 화면을 그리다 멈추고 사용자 입력을 먼저 처리하려고요.

테스트 영역은 사용자가 HTML 코드를 자유롭게 쓰는 곳이라, 아주 깊게 중첩한 입력도 들어올 수 있어요. 2026-11-09 회의에서 Virtual DOM 트리는 **위에서부터 생성하며 부모에 바로 연결**하기로 정했어요.

## 고려한 선택지

### 선택지 A: 재귀

함수가 노드 하나를 처리하고, 자식마다 자기 자신을 다시 불러요. 다음에 갈 곳은 JavaScript 엔진의 콜 스택이 기억해요.

- 장점: 코드가 트리 모양과 닮아 가장 짧고 설명하기 쉬워요.
- 단점: 트리가 아주 깊으면 콜 스택이 넘쳐요(Stack Overflow). 사용자 입력 깊이를 우리가 정할 수 없어요.

### 선택지 B: 반복문과 명시적 스택

다음에 처리할 노드를 배열(스택)에 직접 쌓고, 반복문으로 하나씩 꺼내 처리해요.

- 장점: 콜 스택을 쓰지 않아 아주 깊은 트리에서도 넘치지 않아요. 스택이 배열이라 지금 어디까지 처리했는지 디버거와 로그로 바로 볼 수 있어요.
- 단점: 재귀보다 코드가 길어요. 자식을 넣는 순서를 틀리면 형제 순서가 뒤집혀요.

### 선택지 C: Fiber

노드마다 첫 자식, 다음 형제, 부모를 가리키게 만들고 그 포인터를 따라 반복문으로 순회해요.

- 장점: 작업을 멈췄다 이어서 할 수 있고, 콜 스택도 넘치지 않아요.
- 단점: Virtual DOM 노드를 Fiber 노드로 바꾸는 단계와 포인터 관리가 더해져 구현량이 가장 많아요. 작업을 멈춰야 할 만큼 큰 트리가 이번 과제에는 없어요.

## 결정

변환, Diff, Patch 모두 선택지 B(반복문과 명시적 스택)로 순회한다.

1. 순서는 깊이 우선 전위 순서로 한다. 부모를 먼저 만들거나 처리하고 자식으로 내려간다.
2. 노드를 만들면 바로 부모(또는 결과 배열)에 붙인다.
3. 스택의 항목에는 처리할 노드와 붙을 곳을 함께 담는다.
4. 스택은 마지막에 넣은 것이 먼저 나오므로, 자식은 **뒤에서부터** 넣어 앞 자식부터 처리되게 한다.

## 근거

- 사용자가 깊게 중첩한 HTML을 넣어도 페이지가 Stack Overflow로 멈추지 않아요.
- 회의에서 정한 "위에서부터 생성하며 부모에 바로 연결"은 스택 항목에 붙을 곳을 함께 담으면 그대로 구현돼요.
- "다음 할 일을 꺼내 처리하는 반복문" 구조는 Fiber의 작업 루프와 같은 틀이라, Phase 2에서 작업을 나눠 처리해야 할 때 옮겨 가기 쉬워요.
- Fiber는 이번 일정과 트리 크기에 비해 구현량이 커요.

## 예상되는 결과

- 긍정적 영향:
  - 입력 깊이와 상관없이 변환, Diff, Patch가 끝까지 동작해요.
  - 스택 내용을 찍어 순회 과정을 디버깅하고 발표에서 단계별로 보여 줄 수 있어요.
- 부정적 영향 / 리스크:
  - 재귀보다 코드가 길고 처음 읽을 때 이해하기 어려워요.
  - 자식을 넣는 순서를 틀리면 형제 순서가 뒤집혀요. 자식이 셋 이상인 요소로 순회 순서를 단위 테스트해요.
  - 재귀와 마찬가지로 한 번 시작하면 끝까지 돌아요. 작업 중단이 필요해지면 Phase 2에서 Fiber를 새 ADR로 검토해요.
