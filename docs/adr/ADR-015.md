# ADR-015: value, checked, selected props는 property와 attribute를 함께 맞추고, 문자열 checked·selected는 켜진 것으로 본다

- 상태: 승인됨
- 관리 범위: mini-react 저장소 (docs/adr)

## 개요

`setProp`이 `value`, `checked`, `selected`를 DOM에 반영하는 방법에 대한 결정이에요. 이 글을 읽으면 왜 property만 바꾸면 Phase 1 검증 페이지가 어긋나는지, property와 attribute를 어떤 규칙으로 함께 맞추는지 알 수 있어요.

## 맥락

Phase 2 요구사항 FR-P06은 이 세 props를 "attribute가 아니라 property로" 바꾸라고 정했어요. 사용자가 입력창에 글자를 더 넣으면 property가 attribute와 달라지고, 그 뒤 attribute만 바꾸면 화면이 따라오지 않기 때문이에요. #161에서 `toDOM`과 `patch`가 `setProp`을 부르게 되면서 Phase 1 검증 페이지도 이 규칙을 따르게 됐어요.

그런데 Phase 1은 Virtual DOM 트리를 HTML attribute로 만들고 비교해요(`toVNode`가 `getAttribute`로 읽어요). 그래서 두 가지 문제가 생겼어요.

1. 검증 페이지에서 `<input value="a">`를 Patch하면 실제 영역의 `input`에 `value` attribute가 없어요. `toVNode`로 다시 읽은 트리에 `value`가 빠져 "Patch 후 두 영역이 달라요"가 나오고 기록이 저장되지 않아요(FR-W15).
2. HTML의 `<input type="checkbox" checked>`는 `toVNode`에서 `checked: ''`가 돼요. `el.checked = ''`는 `false`라 체크가 안 된 채로 그려져요.

## 고려한 선택지

### 선택지 A: `setProp`이 property와 attribute를 함께 맞춘다

- 장점: 고칠 곳이 `props.ts` 하나예요. Phase 1과 Phase 2가 같은 `toDOM`, `patch`를 계속 써요. property를 계속 바꾸므로 FR-P06이 막으려던 문제도 그대로 막혀요.
- 단점: FR-P06의 "attribute가 아니라"라는 문장을 고쳐야 해요.

### 선택지 B: Phase 1은 `setProp`을 쓰지 않고 `setAttribute`만 쓴다

- 장점: Phase 1 모듈이 Phase 2 모듈에 기대지 않아요.
- 단점: Phase 1과 Phase 2의 `toDOM`, `patch`가 갈라져요. 과제의 "Phase 1의 Virtual DOM, Diff, Patch를 그대로 활용"과 맞지 않아요.

### 선택지 C: `toVNode`가 property를 읽는다

- 장점: 없어요.
- 단점: 사용자가 입력창에 타이핑할 때마다 Virtual DOM 트리가 바뀌어요. HTML 코드가 원본이라는 Phase 1의 전제가 깨져요.

## 결정

`value`, `checked`, `selected` props는 property와 attribute를 함께 맞춘다.

1. `setProp`은 property를 바꾼다. `value`는 문자열로 바꿔 넣는다. `checked`, `selected`는 값이 문자열이면 값과 상관없이 `true`, 아니면 `Boolean(값)`을 넣는다. 값이 `null`, `undefined`면 빈 값(`''`, `false`)을 넣는다.
2. `setProp`은 이어서 attribute를 다른 props와 같은 규칙(FR-P08, P09)으로 맞춘다. `true`는 빈 문자열로 붙이고, `false`, `null`, `undefined`는 지우고, 나머지는 문자열로 붙인다.
3. `removeProp`은 property를 빈 값으로 바꾸고 attribute도 지운다.

## 근거

A만 Phase 1과 Phase 2가 같은 `toDOM`, `patch`를 쓰면서 두 문제를 모두 풀어요. property를 먼저 바꾸니 사용자가 입력한 뒤에도 화면이 새 값을 따라와요(FR-P06의 목적). attribute까지 맞추면 `toVNode`로 다시 읽은 트리가 원래 트리와 같아져 Phase 1의 두 영역 비교(FR-W15)와 ADR-013(#166, 제안됨)의 왕복 확인이 통과해요.

문자열 `checked`, `selected`를 켜진 것으로 보는 건 HTML boolean attribute의 뜻 그대로예요. HTML에서는 `checked=""`, `checked="checked"` 모두 있으면 켜진 것이에요. `h`에서 넘기는 값은 boolean이라 이 규칙에 영향을 받지 않아요.

## 예상되는 결과

- 긍정적 영향: Phase 1 검증 페이지에서 `value`, `checked`, `selected`가 든 HTML 코드를 Patch해도 두 영역이 같고, 체크박스가 체크된 채로 그려져요.
- 긍정적 영향: Phase 2의 `h`로 만든 입력창도 attribute가 property와 같아 개발자 도구에서 읽기 쉬워요.
- 부정적 영향 / 리스크: `checked: 'false'`처럼 문자열을 넘기면 켜진 것으로 봐요. `h`에서는 boolean을 넘겨야 해요.
- 부정적 영향 / 리스크: attribute를 바꾸면 폼의 초깃값(`defaultValue`, `defaultChecked`)도 바뀌어요. 이 프로젝트는 `form.reset()`을 쓰지 않아 영향이 없어요.

| ID     | 바뀌는 내용 |
| ------ | ----------- |
| FR-P06 | "attribute가 아니라 property로 바꿔야 한다" → "property로 바꾸고, attribute도 FR-P08, P09의 규칙으로 함께 맞춰야 한다. `checked`, `selected`의 값이 문자열이면 켜진 것으로 본다." 확인 방법에 "HTML `<input value="a"><input type="checkbox" checked>`를 `toDOM`으로 그려 `toVNode`로 다시 읽은 트리가 같고 체크박스가 체크돼 있는지 확인"을 더한다 |
| FR-P07 | "그 property를 빈 값으로 바꿔야 한다" → "그 property를 빈 값으로 바꾸고 attribute도 지워야 한다" |
