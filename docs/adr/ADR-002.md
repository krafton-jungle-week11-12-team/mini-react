# ADR-002: Diff는 Phase 1에서 같은 자리, Phase 2에서 key로 노드를 짝짓는다

- 상태: 승인됨
- 관리 범위: mini-react 저장소 (docs/adr)

## 개요

두 Virtual DOM 트리를 비교하는 Diff 알고리즘에 대한 결정이에요. 이 글을 읽으면 Diff가 Phase별로 노드를 어떤 기준으로 짝지어 비교하는지, 왜 key 기반 비교를 Phase 1에서 쓰지 않고 Phase 2에서 쓰는지, 그래서 Phase 1에 어떤 한계가 남는지 알 수 있어요.

## 맥락

FR-E03은 두 Virtual DOM 트리를 비교해 노드 추가, 삭제, 교체, 속성 변경, 텍스트 변경을 찾도록 해요. FR-E04는 바뀐 노드만 실제 DOM에 반영하도록 해요.

두 트리를 가장 적은 횟수로 바꾸는 정확한 방법(트리 편집 거리)은 O(n³)이라 노드가 1,000개면 약 10억 번 연산해야 해요. 그래서 React처럼 두 가지를 가정하고 O(n)으로 비교해요.

- 같은 깊이의 노드끼리만 비교해요.
- 노드 종류나 태그가 다르면 하위 트리를 통째로 교체해요.

남은 문제는 **자식 목록을 어떻게 짝지어 비교하느냐**예요. 테스트 영역의 입력은 사용자가 직접 쓴 HTML 코드라 `key` 같은 식별자가 없어요. ADR-007에 따라 공백·줄바꿈·주석 노드도 자식 목록에 들어가요.

## 고려한 선택지

### 선택지 A: 같은 자리(인덱스)끼리 비교

이전 자식 목록과 새 자식 목록을 같은 번호끼리 비교해요. 남는 쪽은 추가 또는 삭제로 봐요.

- 장점: 구현이 가장 단순하고, 입력에 key가 없어도 그대로 동작해요. 결과를 예측하기 쉬워 테스트 케이스를 만들기 쉬워요.
- 단점: 목록 앞이나 중간에 노드를 끼우면 그 뒤의 노드가 모두 바뀐 노드로 잡혀요. 순서만 바뀐 경우도 이동이 아니라 텍스트 변경이나 교체로 처리돼요.

### 선택지 B: key 기반 비교

이전 자식을 key로 해시 테이블(`Map`)에 넣고, 새 자식마다 같은 key를 찾아 짝지어요. React가 쓰는 방식이에요.

- 장점: 끼우기, 삭제, 순서 변경이 있어도 실제로 바뀐 노드만 잡혀요.
- 단점: 사용자가 쓴 HTML에는 key가 없어요. `id` 같은 속성을 key로 쓸 규칙을 따로 정해야 하고, key가 없는 노드(공백·주석 노드 포함)를 위해 결국 A도 함께 구현해야 해요. 노드 이동까지 처리해야 해서 Patch도 복잡해져요.

### 선택지 C: 최장 증가 수열(LIS) 기반 비교

key로 짝을 지은 뒤, 순서가 이미 맞는 노드를 최대로 남겨 이동 횟수를 최소로 만들어요. Vue 3가 쓰는 방식이에요.

- 장점: DOM 이동 횟수가 가장 적어요.
- 단점: B의 단점을 모두 가지면서 구현이 가장 어려워요. 이번 샘플 HTML 규모에서는 차이를 체감하기 어려워요.

## 결정

Diff는 같은 깊이의 노드끼리 비교하고, 자식 목록을 짝짓는 기준은 Phase마다 다르게 한다.

- Phase 1: 선택지 A(같은 자리(인덱스)끼리 비교)를 쓴다.
- Phase 2: 선택지 B(key 기반 비교)로 바꾼다. key 규칙과 key가 없는 노드의 처리는 Phase 2 설계에서 정한다.

노드 한 쌍은 아래 순서로 판단한다.

1. 이전 노드만 있으면 삭제
2. 새 노드만 있으면 추가
3. `kind`가 다르거나, 둘 다 요소인데 `tag`가 다르면 교체. 하위 트리는 더 비교하지 않는다.
4. 둘 다 텍스트 노드 또는 둘 다 주석 노드인데 `text`가 다르면 텍스트 변경
5. 둘 다 요소면 `props`를 비교해 다르면 속성 변경. 그다음 자식 목록을 짝지어(Phase 1은 같은 자리끼리) 1번부터 다시 판단한다.

이 판단 순서는 Phase 2에서도 그대로 쓰고, 자식 목록을 짝짓는 부분만 바꾼다. 선택지 C(LIS 기반 비교)는 쓰지 않는다.

## 근거

- 입력에 key가 없어요. B와 C는 key 규칙을 새로 만들어야 하고, key가 없는 노드 때문에 결국 A도 구현해야 해요.
- A로도 FR-E03의 다섯 경우를 모두 찾을 수 있고, 바뀌지 않은 노드는 그대로 두므로 FR-E04를 만족해요.
- 화면 결과는 A, B, C 모두 같아요. 차이는 바뀐 노드로 잡히는 개수와 DOM 호출 횟수예요.
- 일정상 Phase 2(Component, State, Hooks)에 시간을 남겨야 해요.
- Phase 2에서는 컴포넌트가 State를 가져서, 같은 자리 비교로는 State가 엉뚱한 항목에 남아 화면 결과가 틀려질 수 있어요. 컴포넌트 코드에는 key를 직접 붙일 수 있어 B의 첫 번째 단점도 사라져요.
- C는 B보다 DOM 이동 횟수만 줄여 줘요. 화면 결과는 같고 구현은 가장 어려워요.

## 예상되는 결과

- 긍정적 영향:
  - Diff와 Patch 구현이 단순해져요.
  - 다섯 가지 변경 종류를 경우별로 테스트하기 쉬워요.
- 부정적 영향 / 리스크:
  - 목록 앞이나 중간에 노드를 끼우면 뒤의 노드가 모두 바뀐 노드로 잡히고 강조 표시돼요. 발표와 문서에 한계로 적어요.
  - Phase 2에서 컴포넌트가 State(체크 상태, 입력값 등)를 가지면, 인덱스 비교 때문에 State가 엉뚱한 항목에 남을 수 있어요. 이때는 화면 결과도 틀려지므로 Phase 2에서 key 기반 비교로 바꿔요.
  - Phase 2에서 바꾸기 쉽게, Diff 설계에서 "자식 목록을 짝짓는 부분"을 별도 함수로 나눠요.
  - Phase 2에서는 노드 이동과 목록 중간 삽입이 생겨 Patch도 함께 바꿔야 해요.
